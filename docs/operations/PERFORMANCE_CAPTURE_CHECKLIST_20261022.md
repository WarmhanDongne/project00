## 목적과 비교 대상

**기존 release 영상과 새 release 영상을 같은 화면 기준으로 분석해, 그룹 생성·추방·초기화가 몇 초·몇 % 달라졌는지 확인한다.** 이번 문서는 테스트 지시문이며 아직 개선 후 측정 결과는 없다. APK 생성·배포와 실제 기기 설치·촬영 완료를 구분한다.

| 구분 | 기준 |
| --- | --- |
| 개선 전 PRE | `android-release-develop-b921f53-20261016`, `1.0.0+4`, 사용자가 10/17 촬영한 기존 영상 |
| 개선 후 POST | `android-release-room-actions-cc293dff-wip-20261022`, `1.0.0+6`, 이번 변경 포함 APK. 정확한 SHA-256·배포 시각은 release 기록 참조 |

비교는 이전 영상의 UI 피드백 시작부터 같은 완료 화면까지를 기준으로 한다. 새로운 영상에 터치 표시가 있어도 이전 영상에 없던 **물리 터치 시작 시간으로 기준을 바꾸지 않는다.** 터치→화면 피드백 지연은 새 영상의 보조 지표로만 분리한다.

## 사용자가 실행할 순서

### 1. 준비

1. release 기록의 새 APK를 태블릿과 참여 휴대폰 모두에 설치한다. 같은 APK를 사용한다. 서명이 맞지 않아 설치가 실패하면 중단하고 알린다. 기존 앱·데이터를 삭제해 해결하지 않는다.
2. 기존과 같은 태블릿·휴대폰·계정·Wi-Fi를 사용하고 로그인·권한 팝업은 먼저 끝낸다. 첫 요청을 측정하기 전에 예비 생성/추방/초기화를 실행하지 않는다. 이미 실행했다면 첫 관측 표본임을 AI가 기록한다.
3. 기존 영상과 참가 인원을 맞춘다. 기본은 태블릿 1대와 휴대폰 A 1대다. 기존 비교 구간에 B도 참가했다면 B도 같은 시점에 참가시킨다. 한 명/두 명인 결과를 섞지 않는다. 모델·OS·APK 확인 기록은 AI가 정리하고 사용자의 동작별 수기 시각표는 요구하지 않는다.
4. 날짜·시간 자동 설정, 같은 화면 방향·배율·언어와 기존과 비슷한 녹화 조건을 유지한다. 배터리 절전·네트워크 전환·백그라운드 진입을 피한다. 측정 중 재배포·다른 기기의 같은 그룹 조작을 하지 않는다.
5. 태블릿과 휴대폰 A에서 녹화를 시작한다. 가능하면 터치 표시를 켠다. B까지 종료 반영을 판정하려면 B 영상도 남긴다. B 영상이 없으면 B 완료 시각은 미확인으로 둔다.
6. 가능하면 한 카메라에 태블릿과 휴대폰을 동시에 담은 영상도 남긴다. 화면 녹화만 사용할 경우 녹화 시작/끝에 양쪽에서 확인 가능한 공통 시각·동기화 단서를 남긴다. 파일 저장 시각만으로 두 영상을 정렬하지 않는다. 단서가 부족해도 태블릿 자체 지표는 분석할 수 있다.

기존 확인 기기: 태블릿 SM-P610/Android 13, 휴대폰 A SM-A356E/Android 15. 이는 10/17 기록이며 이번 현재 상태는 설치 확인 때 다시 기록한다. 기기 일련번호·계정 식별자는 공개 보고서에 넣지 않는다.

### 2. 아래 로비 묶음을 최대 5회 반복

| 순서 | 사용자 행동 | 기다릴 완료 상태 |
| --- | --- | --- |
| 1 | 태블릿에서 `초대하기/그룹 생성`을 한 번 누른다 | 덮개가 걷히고 방 코드·초대 카드가 정상 표시됨 |
| 2 | 휴대폰 A로 참가한다. 기준이 2명이면 B도 참가한다 | 태블릿 명단과 각 휴대폰 대기실이 정상 표시됨 |
| 3 | 태블릿에서 A의 `내보내기`를 한 번 누른다 | 태블릿에서 A가 사라지고 A에도 퇴장이 반영됨 |
| 4 | A에서 직접 다시 참가한다 | 양쪽 참가 상태가 다시 정상 표시됨 |
| 5 | 태블릿에서 `초기화`를 한 번 누른다. 확인창이 있으면 최종 확인을 누른다 | 태블릿이 그룹 없는 화면으로 돌아오고 참가 휴대폰에도 종료가 반영됨 |

- 각 동작의 완료 뒤 다음 조작까지 약 10초를 둔다. 생각 시간·참가·재참가·10초 간격은 세 동작의 처리 시간에 더하지 않는다.
- 추방 대상은 기본 A로 고정한다. B 추방도 별도 확인하려면 A의 추방 반영이 끝난 뒤 약 10초 후 한 명씩 실행한다. 동시에 두 명을 추방하지 않는다. 대상·추방 직전 인원을 나눠 집계한다.
- 1~5를 한 묶음으로 하여 최대 5묶음을 연속 녹화한다. 첫 묶음과 2~5번째 묶음을 구분하고, 묶음마다 앱을 재시작하거나 캐시를 지우지 않는다.
- 2~5번째 생성 성공으로 직전 초기화 후 같은 계정의 재생성을 확인한다. 5번째 초기화 뒤에는 생성 1회만 추가해 새 그룹이 정상 유지되는지 약 30초 확인한다. 이 여섯 번째 생성은 후속 기능 확인이며 기본 5회 속도 표본에 합치지 않는다. 확인 후 정상 초기화로 테스트 그룹을 정리한다.
- 게임을 시작하지 않아도 이번 세 동작의 개선도 측정은 가능하다. 단독 태블릿 초기화와 참가자 있는 초기화는 따로 분류한다.

### 3. 오류가 나면

- 연타하지 않는다. 결과가 미확정이거나 멈추면 그 묶음을 중단하고 화면·오류 문구를 녹화에 남긴다. 이후 재시도는 정상 성공 표본과 분리한다.
- 앱 재시작·잠금·백그라운드·Wi-Fi 전환이 있었다면 그 사실만 알려준다. AI가 영상 위치를 찾아 표본에 표시한다.
- 실패·중단 표본을 조용히 버리거나 성공 시간을 0초로 채우지 않는다. 표본을 채우려고 추가 반복하지 않으며 유효 건수가 적으면 그대로 보고한다.

### 4. 촬영 뒤 전달

- 태블릿/A/B 역할을 구분할 수 있는 원본 영상과 기존 10/17 영상 또는 기존 분석 자료를 보관·전달한다. 이미 보관된 기존 자료는 다시 촬영하지 않는다.
- 앞뒤를 잘라낸 편집본만 남기지 말고 원본의 metadata·프레임 정보를 보존한다. 사용자가 동작별 시간을 수기로 적을 필요는 없다.
- AI는 파일명·SHA-256·역할·촬영 구간·표본 ID와 예외를 정리한다. 공유용 이미지/영상/보고서에는 계정·방 코드·비공개 정보를 가린다.
- 로그 수집은 이 문서로 자동 시작되지 않는다. release의 debug 전용 통신 진단을 요구하지 않는다. 서버 로그가 필요하면 [조회 절차](FIREBASE_SERVER_LOGS.md)에 따라 함수·시간·최대 건수와 조회용 계정 확인을 별도로 합의한다. 기본 비교는 영상으로 진행할 수 있다.

현재 구현은 초기화 버튼에서 바로 서버 close를 시작한다. 확인창 대기나 사용자가 읽는 시간을 처리 시간에 포함하지 않는다. 덮개/QR의 연출 시간도 영상에 보인 사용자 체감에 포함하되, 서버 응답 시간으로 바꾸어 부르지 않는다. 화면 모양이 바뀌어 같은 경계를 찾을 수 없으면 해당 비교는 제외·사유 기록한다.

AI는 먼저 전체 영상을 탐색해 행동을 식별하고, 이전 분석처럼 로비는 0.25초 간격으로 경계를 좁힌다. 원본이 있으면 전후 모두 같은 정밀도로 프레임/PTS를 확인할 수 있다. 새 영상만 더 촘촘히 재서 정밀도가 같은 것처럼 표현하지 않는다.

- 각 시작/완료를 마지막 미충족~첫 충족 프레임의 구간으로 남긴다.
- 시작이 `[s0,s1]`, 완료가 `[e0,e1]`이면 지속 시간 구간은 `[max(0,e0-s1), e1-s0]`이며, 대표값은 두 경계 중간값의 차이로 계산한다. 대표값은 순수 서버 시간이나 물리 입력 지연이 아니다.
- 기기 간 정렬 오차는 K-A/R-A/R-ALL의 시간 구간에 추가한다. 과거 A/태블릿 정렬의 약 0.5초 불확실성을 무시하지 않는다. 새 영상도 정렬 근거가 없으면 기기 간 소요 시간은 `확정 불가`로 둔다.
- 첫 관측 요청은 별도 행으로 보고하고 cold start로 확정하지 않는다. 반복 중앙값은 원칙적으로 묶음2~5의 정상·비중첩 표본에서 산출한다.

### 개선도 계산과 결론

같은 지표·기기·인원·완료 경계·첫/반복 구분이 맞는 PRE/POST만 비교한다. PRE/POST는 배포 조합 구분이며 휴대폰 A/B 역할과 다르다.

```text
반복 대표값 = 해당 조건의 정상 표본 중앙값
단축 시간(초) = 이전 중앙값 - 이후 중앙값
단축률(%) = (이전 중앙값 - 이후 중앙값) / 이전 중앙값 × 100
```

- 음수면 느려진 것으로 그대로 표시한다. 이전 값이0이거나 자료가 없으면 단축률을 계산하지 않는다. 최초값과 반복 중앙값을 섞지 않는다.
- 표본 수·범위·최대값·실패/재시도/제외 건수와 이유를 함께 보고한다. 5회로 안정적인 p95나 통계적 유의성을 주장하지 않는다.
- 변화가 경계/정렬 불확실성 안에 있으면 `유의미한 차이 확인 어려움`으로 판정한다. 0.25초 간격 분석으로 수십 ms 개선을 확정하지 않는다.
- PRE는10/17의 앱+당시 서버, POST는이번 앱+배포 서버다. 그 사이 develop의 로비 대기 단축·로고·네이티브 변경도 포함돼 **이전 배포 조합 대비 관측 변화**를 뜻한다. 이번 세 코드 변경만의 순수 기여율로 단정하지 않는다.
- 서버를 업데이트한 뒤 예전 APK를 다시 실행해도 예전 서버 상태가 재현되지 않는다. 원래 비교 영상이 없으면 과거 조합 개선율은 `측정 불가`이며 새 조합의 절대 시간만 확보한다. 운영 rollback이나 구 APK 강제 다운그레이드는 이 절차에 포함하지 않는다.
- 생성·추방·초기화의 초 단위 개선과 함수 내부 시간·DB 다운로드량·저장량·비용 개선은 구분한다. 영상만으로 DB/요금 감소를 계산하지 않는다.
