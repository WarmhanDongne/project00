# 개발 전 현재 기준 — 로그인·네트워크·세션 수동 테스트

작성일: 2026-10-04 · 현재 결과: **모든 항목 미실행**

## 1. 무엇을 테스트하나

현재 앱에서 로그인, 방 참가, 네트워크 복구, 앱 재실행, 게임 중단·시간 보존,
퇴장·강퇴·종료, 게임별 연출과 화면을 확인한다. 발견한 문제는
[공식 작업 목록](../planning/TASKS.md)에 정리한다.

- 과거에 통과한 기능도 다시 테스트한다. [8월 기록](REAL_DEVICE_AUTH_NETWORK_SESSION_CHECKLIST.md)은 그대로 둔다.
- [회귀 검토 요약](../planning/logs/2026-10.md#회귀-검토-요약과-작업-순서)의 가설은 직접 확인한 실패와 구분한다.
- **검증 목표**는 앞으로 확인할 동작이다. 이 문서로 새 복구 정책을 확정하지 않는다.
- 비용·전체 보안 감사·배포·다운로드/패치 검증·일반 디자인·튜토리얼 설계는 별도 작업이다.

Codex가 실행할 때는 [Android Emulator 실행 준비](EMULATOR_TEST_EXECUTION.md)를 따른다.
ADB 조작 확인만으로 아래 제품 테스트를 통과 처리하지 않는다.

## 2. 테스트 준비

### 공통 정보 — 시작할 때 한 번만 적기

| 항목 | 기록 |
| --- | --- |
| 테스트 날짜·회차 | |
| 설치 앱 버전·debug/release | 소스 커밋을 알면 함께 적기 |
| 서버 환경·버전 | 모르면 미확인 |
| 기기·OS·실물/에뮬레이터 | |
| 인터넷 연결 방식·글씨/화면 확대 설정 | |

앱이나 서버가 바뀌면 새 회차로 기록한다. 설치 앱·서버 버전을 로컬 HEAD와 같다고 가정하지 않는다.
기존 앱을 삭제하거나 앱 데이터·저장 세션을 지우지 않는다.

### 기기와 계정

| 별칭 | 역할 |
| --- | --- |
| T | 방을 만들고 게임을 진행하는 태블릿 |
| A | 주로 인터넷을 끄거나 앱을 재실행할 휴대폰 |
| B | 비교할 정상 휴대폰. 지정된 경우에만 함께 단절 |
| C / D | 4인 게임에 추가할 휴대폰 |
| X | 방에 참가하지 않은 외부 계정 |

각 기기는 서로 다른 테스트 계정을 쓴다. 계정은 별칭으로만 적는다.

| 게임 | 기본 준비 |
| --- | --- |
| Liar's Poker (LP) | T + A/B, 현재 게임이 허용하는 구성 |
| Final Call (FC) | T + A/B/C/D, 4인 2대2 자리 구성 |
| Mafia | T + A/B/C/D, 최소 4명과 유효 역할 배치 |

인원·기기·게임이 없으면 해당 항목을 **미실행**으로 남긴다.
게임·Android/iOS·실물/에뮬레이터 결과는 따로 적는다.
유료 게임 비교에는 이미 준비된 게임을 쓰고, 없으면 해당 경우를 미실행으로 둔다.

### 인터넷 끄기·복구 확인

1. 완전 단절은 Wi-Fi와 모바일 데이터를 모두 끈다. 네트워크 전환은 별도로 테스트한다.
2. 인터넷 끄기 → T의 중단 표시 확인 → 인터넷 켜기 → 현재 화면에서 실제 조작까지 확인한다.
3. 타이머는 단절 직전, **T에 중단이 표시된 때**, 복구 후 값을 비교한다.
4. 복구는 우선 60초, 가능하면 총 120초까지 관찰한다. 걸린 시간과 재시도·재실행 필요 여부를 적는다.

인터넷을 켠 순간과 앱이 다시 연결된 순간은 다를 수 있다.
관찰 시간은 통과 제한 시간이 아니다. 지연만으로 판정하기 어려우면 **판정 대기**로 둔다.
장기 단절·중단 투표 마감·방 보존 경계는 별도 방에서 테스트하고, 방 종료와 복구 실패를 구분한다.

## 3. 실행 순서와 결과

1. 가능한 로그인(AUTH-01/02/03) → 방 생성·참가(ROOM-01).
2. 주요 문제: ROOM-04 → NET-02~08 → RESTORE-02~04 → EXIT-02/06/07.
3. 나머지 A~H를 진행한다. 개발자 보조가 필요한 항목과 I는 별도로 진행한다.

| 결과 | 적는 기준 |
| --- | --- |
| 통과 | 해당 조건의 조작과 확인 항목을 모두 확인함 |
| 실패 | 기대 동작과 다른 현상을 직접 확인함 |
| 판정 대기 | 시도했지만 정책·내부 상태·장애 발생 여부가 불확실함 |
| 미실행 | 아직 하지 않았거나 준비가 부족함 |
| 해당 없음 | 그 게임·기기에 없는 기능이나 상태임 |

빈 기록은 미실행이다. 일부만 확인했다면 전체 통과로 적지 않는다.
문제가 재현되지 않으면 시도 횟수를 남기고, 해결됐다고 단정하지 않는다.

각 항목의 기록란에 결과를 적는다. 문제가 있거나 확인하지 못했다면
**게임·단계·기기 / 실제 증상 / 재시도·재실행 결과 또는 미확인 이유**만 짧게 덧붙인다.
조건이 달라지면 결과를 따로 적는다. 영상·화면·로그가 있으면 위치를 함께 남긴다.

공유 자료에서는 이메일·방 코드·UID·token·손패·역할·조사 결과를 가린다.
개인 데이터는 테스트자가 직접 비교하고 값 자체는 문서에 적지 않는다.

## 7. 관찰 결과를 직접 task로 옮기기

첫 정리에서는 실패·판정 대기·미실행을 나누고, 기존 task가 같은 문제를 다루는지 확인한다.
같은 현상은 재현 조건을 기존 task에 추가하고 다른 현상은 신규 후보로 둔다.
구현 원인과 과거 대비 변화가 확인되기 전에는 “회귀 확정”이라고 쓰지 않는다.

| 후보 | 시나리오·실행 ID | 관찰 사실 | 분류 | 기존 task/신규 후보 | 영향·우선순위 제안 | 다음 행동 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | 실패/정책 확인/검증 공백/UX | | | |

task 하나는 다음 형식으로 작성한다.

```text
ID / 제목: [동작 조건]에서 [관찰한 문제]
상태: 조사 전 / 요구사항 확인 / 관찰 중
목적·사용자 영향:
재현 환경: 앱·서버 후보, 게임·단계, 인원, 기기·OS
재현 절차: 시나리오 ID + 실제 조작 차이
관찰 사실: 무엇이 실제로 일어났는가
원인 가설: 아직 모르면 미확인
과거 대비: 유지 / 보완 / 새 회귀 / 기존 결함 / 미확인
지켜야 할 계약·확인이 필요한 제품 정책:
담당 범위: 플랫폼 / 서버 / game_kit / 개별 게임 / 검증
완료 조건: 같은 조건에서 어떤 결과를 확인하면 해결인가
필요한 검증: 자동 재현 / 실기기 재검증 / 계약·운영 확인
다음 행동:
관련 실행 ID·근거·기존 task:
```

예시(실행 결과가 아닌 작성 예):

> NET-05에서 A/B 단절 후 A만 복귀했는데 턴이 진행됐다고 직접 확인한 경우:
> “두 참가자 단절 후 한 명만 복귀할 때 남은 단절 사유를 유지한다”를
> SESSION-RECONNECT-02의 재현 조건과 완료 조건에 추가한다.
> 서버·실기기 원인이 확인되지 않았으면 해당 부분은 가설로 둔다.

세션/상태 유실, 중복 행동, 타인 데이터 노출, 진행·퇴장 불가는 우선 검토한다.
순수 체감 지연·안내 혼란·레이아웃은 영향과 재현 범위를 적어 따로 판단한다.
실행할 수 없었던 핵심 항목도 “문제 없음”으로 버리지 않고 기기 확보·보조 재현 등
검증 task로 남긴다. 우선순위·출시 차단·담당 범위는 공식 TASKS에서 사용자/팀이 결정한다.

## 8. 자동 검사·보조 환경의 경계

수동 테스트 결과를 모으기 위해 테스트 복원이나 앱 수정을 먼저 해야 하는 것은 아니다.
현재 앱의 정상 조작으로 확인할 항목부터 기록할 수 있다. 반대로 자동 검증 통과는
물리 기기·iOS의 단절 시간과 앱 lifecycle을 대신하지 않는다.

현재 검토 기준으로 session/auth가 참조하는 Flutter 파일 20개가 없고 package 테스트의
공식 실행 배선도 확인 대상이다. 이번 문서 작성으로 복원하지 않았다.
실행 전 [Project CLI](../engineering/PROJECT_CLI.md)의 플랫폼 경로를 읽는다.

Windows:

```powershell
.\tool\invoke_mosigame.ps1 test session
.\tool\invoke_mosigame.ps1 test auth
.\tool\invoke_mosigame.ps1 validate --full
```

macOS/Linux:

```sh
dart run :mosigame test session
dart run :mosigame test auth
dart run :mosigame validate --full
```

| 실제 실행 명령 | 실행 후보·시각 | status | exit code | 실행/미실행 범위·누락 | 전후 working-tree 상태 |
| --- | --- | --- | --- | --- | --- |
| session | 미실행 | — | — | | |
| auth | 미실행 | — | — | | |
| FULL | 미실행 | — | — | | |
| CI/package 실행 목록 확인 | 미실행 | — | — | | |

명령·status·exit를 추정해서 채우지 않는다. 누락 파일의 INVALID, 환경 BLOCKED,
제품/검증 FAIL을 구별하며 테스트 삭제·기대값 약화로 통과시키지 않는다.

보조 장애 주입·DB/rules 변경·배포는 합의된 테스트 환경에서 별도 범위로 수행한다.
이 문서는 production 조회·쓰기·Auth 접근·서버 설정 변경을 승인하지 않는다.
production RTDB 관찰이 필요하면 [Firebase MCP 절차](FIREBASE_MCP.md)의 사람 확인,
도구 제한, 정확한 단일 경로 사전 승인 조건을 따른다. 원시 데이터 전체를 공유하지 않는다.

## 9. 테스트 회차 마감

- 적용 가능한 시나리오마다 실행 결과 또는 미실행 이유를 남겼다.
- 결과의 게임·단계·기기·앱 빌드·서버 확인 범위를 명시했다.
- 실패 현상과 원인 가설, 기존 기능 실패와 새 정책 요구를 구분했다.
- 과거 완료 판정을 보존하고 현재 후보의 관찰 근거를 별도로 연결했다.
- 실패·판정 대기·검증 공백에서 도출한 후보를 정리했다.
- 확정할 작업은 [TASKS.md](../planning/TASKS.md)에 반영하고 의미 있는 관찰은
  [10월 기록](../planning/logs/2026-10.md)에 실행일·근거와 함께 남긴다.
- 최종 수정 후보 재검증에서는 동일 시나리오 ID를 사용하고 새 실행 ID를 부여한다.

문서에 항목이 존재하는 것, 테스트 절차를 작성한 것, 현재 후보를 실제 실행한 것은
서로 다른 상태다. 이번 문서의 모든 제품 테스트 결과는 사용자 실행 전까지 미실행이다.
