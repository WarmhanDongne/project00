# 작업 관리 방법

## 문서 역할

| 문서 | 관리 내용 |
| --- | --- |
| [작업 목록](TASKS.md) | 현재 작업의 분류·상태·다음 행동 요약 표 |
| [작업별 상세](tasks/) | 목적·현상, 범위·승인 경계, 근거·완료 조건, 관련 코드와 기록 |
| 이 문서 | 공통 관리 규칙·출시 판정 기준 |
| [완료 작업](COMPLETED_TASKS.md) | 완료 작업의 요약·완료일·상세 링크 |
| [월별 기록](logs/) | 날짜별 조사·결정·실행·검증 과정 |

현재 분류·상태·다음 행동의 단일 원본은 TASKS.md다. 상세 파일에는 이를 별도 현재 상태 표로
복제하지 않고 작업 설명과 날짜가 붙은 결정·검증 근거를 남긴다. 기술 문서는 현재 구현의
단일 원본이며, 작업 설명·일지로 대체하지 않는다.

## 작업별 상세 파일 작성

- 파일은 `tasks/<TASK-ID>.md`, 첫 제목은 `# <TASK-ID>`로 고정하고 다음 줄에 작업명을 적는다.
- TASKS.md의 ID는 `tasks/<TASK-ID>.md#<소문자-task-id>`로 연결한다.
  분류 변경 때는 목록 행만 옮기고 상세 파일 경로는 바꾸지 않는다.
- 상세 파일 상단에는 작업 목록과 관리 방법으로 돌아가는 링크를 둔다.
- 목적·사용자 보고, 확인 근거·미확인 사항, 작업 범위·승인/보류 조건, 완료 조건·필요한 검증,
  관련 작업·코드·월별 기록을 관리한다. 기존 짧은 항목은 내용을 임의로 보충하지 않는다.
- 날짜가 붙은 과거 상태·분류·다음 행동은 당시 근거로 보존한다. 현재 판정과 구분한다.

## 관리 방법

- 작업 ID는 문서 이동·월 변경 후에도 유지한다. 상태는 `조사 전`, `요구사항 확인`,
  `관찰 중`, `진행 중`, `검증 대기`, `보류`로 구분하고, 보류에는 이유를 적는다.
- 사용자 보고, 코드·측정으로 확인한 사실, 원인 가설과 제안을 구분한다. 2026-08-31 신규
  항목의 등록일은 해당 날짜이며 이후 항목은 각 등록일을 적는다. 목록에 있다는 사실은
  조사·구현·승인 완료를 뜻하지 않는다.
- 필수 항목만 출시 차단으로 관리한다. 권장·출시 후 항목을 필수로 바꿀 때는 근거와
  결정을 기록한다. 비용·보안·핵심 구조 점검은 범위를 먼저 명시하고 무제한 최적화를
  완료 조건으로 삼지 않는다.
- 각 항목에 목적·현상, 완료 조건, 다음 행동, 관련 기록을 유지한다. 상세 진행은
  Issue/PR을 사용할 수 있지만 장기 결정과 완료 조건은 해당 작업의 상세 파일에 남긴다.
  기존 출시 후 관찰 항목은 착수 승인 시 Issue를 만들고 연결하는 절차를 유지한다.
- 완료 조건과 필요한 검증을 충족하면 목록 행을 완료 문서로 옮기고 상세 파일을 연결한다.
  상세 파일은 같은 경로에 보존하고 완료일·변경 내용·검증 근거·한계를 갱신한다.
  상세 파일의 돌아가기 링크는 완료 문서로 바꾼다. 일부만 완료하면 남은 범위를 작업 목록에
  유지한다. 취소는 완료와 구분해 이유를 기록한다.
- 기록은 `logs/YYYY-MM.md`에 태스크별로 모으고 각 태스크 안에서는 날짜순으로 쓴다.
  파일 상단에는 날짜별 링크 목차만 둔다. 여러 달의 기록 링크는 해당 작업/완료 항목에
  모은다. 공통 검증은 한 번 기록하고 관련 ID들에서 연결한다.
- 일지에는 의미 있는 조사·수정·실패·판단·검증만 남긴다. 검증은 명령, status, exit code,
  확인 범위와 필요 시 기기·빌드를 적고 credential·token·불필요한 사용자 데이터는 넣지 않는다.
- 현재 구현 설명을 일지로 대체하지 않는다. 구조·동작을 바꾸면 기존 기술 문서도
  갱신한다. 승인·검증은 [Engineering Contract](../engineering/ENGINEERING_CONTRACT.md)와
  [Project CLI](../engineering/PROJECT_CLI.md)를 따른다. 기록된 과거 승인을 새 작업에 재사용하지 않는다.

## 출시 판정 기준

다음 조건을 모두 만족해야 작업 목록의 출시 차단을 해제한다.

1. 신규 미해결 항목을 포함한 모든 차단 항목에 필요한 코드 수정과 관련 회귀 테스트가
   완료된다.
2. 관련 Flutter 분석·테스트와 Functions build·테스트가 통과한다.
3. Project CLI targeted suite와 `validate --full`이 통과한다.
4. 필요한 Functions만 승인된 절차로 배포하고 배포 후 동작을 확인한다.
5. 수정 완료 뒤 작성한 최종 실제 기기 체크리스트가 통과한다.
6. 실행 명령, exit code, 배포 함수, 실기기와 production 관찰 근거를 출시 기록에 남긴다.

위 기준은 기존 구현 변경의 출시 판정 조건을 보존한 것이다. 작업 목록의 권장·출시 후
작업을 자동으로 출시 차단으로 올리거나 과거 통과 범위를 확대하지 않는다.
