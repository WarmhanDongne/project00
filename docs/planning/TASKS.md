# 작업 목록

현재 해야 할 일과 진행 상태의 단일 원본이다. 출시 시점은 문서 경계가 아니라 항목의
분류로 관리한다. 완료 결과는 [완료 문서](COMPLETED_TASKS.md), 과정은
[월별 기록](logs/2026-08.md), 현재 구현은 [아키텍처](../engineering/ARCHITECTURE.md)와
관련 기술 문서에서 확인한다.

## 관리 방법

- 작업 ID는 문서 이동·월 변경 후에도 유지한다. 상태는 `조사 전`, `요구사항 확인`,
  `관찰 중`, `진행 중`, `검증 대기`, `보류`로 구분하고, 보류에는 이유를 적는다.
- 사용자 보고, 코드·측정으로 확인한 사실, 원인 가설과 제안을 구분한다. 이번 신규
  항목의 등록일은 2026-08-31이며, 목록에 있다는 사실은 조사·구현·승인 완료를 뜻하지 않는다.
- 필수 항목만 출시 차단으로 관리한다. 권장·출시 후 항목을 필수로 바꿀 때는 근거와
  결정을 기록한다. 비용·보안·핵심 구조 점검은 범위를 먼저 명시하고 무제한 최적화를
  완료 조건으로 삼지 않는다.
- 각 항목에 목적·현상, 완료 조건, 다음 행동, 관련 기록을 유지한다. 상세 진행은
  Issue/PR을 사용할 수 있지만 장기 결정과 완료 조건은 이 문서에 남긴다. 기존 출시 후
  관찰 항목은 착수 승인 시 Issue를 만들고 연결하는 절차를 유지한다.
- 완료 조건과 필요한 검증을 충족하면 상세 항목과 목록 행을 완료 문서로 옮긴다.
  완료일·변경 내용·검증 근거·한계를 남기고 들어오는 링크도 갱신한다. 일부만 완료하면
  남은 범위를 여기 유지한다. 취소는 완료와 구분해 이유를 기록한다.
- 기록은 `logs/YYYY-MM.md`에 태스크별로 모으고 각 태스크 안에서는 날짜순으로 쓴다.
  파일 상단에는 날짜별 링크 목차만 둔다. 여러 달의 기록 링크는 해당 작업/완료 항목에
  모은다. 공통 검증은 한 번 기록하고 관련 ID들에서 연결한다.
- 일지에는 의미 있는 조사·수정·실패·판단·검증만 남긴다. 검증은 명령, status, exit code,
  확인 범위와 필요 시 기기·빌드를 적고 credential·token·불필요한 사용자 데이터는 넣지 않는다.
- 현재 구현 설명을 일지로 대체하지 않는다. 구조·동작을 바꾸면 기존 기술 문서도
  갱신한다. 승인·검증은 [Engineering Contract](../engineering/ENGINEERING_CONTRACT.md)와
  [Project CLI](../engineering/PROJECT_CLI.md)를 따른다. 기록된 과거 승인을 새 작업에 재사용하지 않는다.

### COST-01

**Functions 과금 점검·최적화**

- 사용자 보고: 유저 없이 개발하는 과정에서 Firebase 과금 약 1,200원이 발생했고,
  Cloud Functions 관련 점검이 필요하다. 실제 청구 서비스·원인은 아직 확인하지 않았다.
- 조사: 청구 기간·항목과 함수 실행 원인, 호출량, 불필요한 반복 실행 여부를 확인한다.
  과금 발생 자체를 비효율의 확정 근거로 삼지 않는다.
- 완료 조건: 비용 원인과 필요한 개선을 정리하고, 수정했다면 전후 실행량·비용 등
  확보 가능한 근거와 회귀 검증을 남긴다. 관찰 기간이 부족하면 효과 확인은 검증 대기로 둔다.

### SECURITY-01

**보안 위험 점검·중대한 문제 수정**

- 사용자 요청: 문제가 발생할 때의 리스크가 크므로 최소한 어떤 문제가 가능한지 점검한다.
- 조사 범위 초안: 인증·인가, Functions 요청 검증, Firebase rules, 공개/개인/서버 데이터
  경계, 비밀정보 노출, 남용 가능성. 실제 코드와 설정을 확인한 범위를 명시한다.
- 완료 조건: 위험·영향·근거·대응을 정리하고 출시 차단 수준의 문제를 수정·검증한다.
  미점검 영역과 남은 위험을 밝힌다. 점검 완료를 모든 보안 위험 부재로 표현하지 않는다.

### TABLET-ASSET-01

**태블릿 게임 구성품 이미지 덮임**

- 사용자 보고: 게임 카드 클릭으로 연 모달에서 구성품 이미지가 로드된 뒤 다른 이미지가
  로드되어 덮인다. 게임·기기·빌드·정확한 재현 조건은 미확인이다.
- 다음 행동: 표시 순서와 의도한 최종 이미지를 확인하고 재현한다. 캐시나 비동기 처리
  문제라고 미리 단정하지 않는다.
- 완료 조건: 원인을 수정하고 모달 재진입·게임 전환 시 올바른 이미지가 유지되는지
  관련 자동 검증과 태블릿 화면 확인 결과를 남긴다.

### TABLET-MEMBERS-01

**태블릿 키보드 등장 시 구성원 목록 깨짐**

- 사용자 보고: 프로필 수정 창에서 닉네임 수정을 위해 키보드가 나타나면 태블릿의
  구성원 목록이 깨지는 경우가 있다. 기기·OS·앱 빌드·확대 설정은 미확인이다.
- 다음 행동: 키보드 표시·숨김과 프로필 창 진입·종료 흐름을 재현한다.
- 완료 조건: 목록 겹침·잘림·overflow 없이 구성원을 확인하고 조작할 수 있으며,
  키보드를 닫은 후 정상 배치로 돌아오는지 관련 자동 검증과 기기 확인을 남긴다.

### TEST-ACCOUNT-01

**배포용 테스트 계정 준비**

- 사용자 요청: 배포를 위한 테스트 계정이 필요하다. 스토어 심사용인지 내부 QA용인지,
  필요한 환경·로그인 방식·권한·인원은 아직 확정하지 않았다.
- 다음 행동: 용도와 접근 범위, 테스트 데이터, 유지·회수 방법을 정한다. production
  계정 생성이나 데이터 쓰기는 이번 문서 등록의 실행 범위가 아니다.
- 완료 조건: 합의한 환경에서 로그인부터 필요한 그룹·게임 흐름을 검증하고 사용 방법을
  남긴다. 비밀번호·인증 토큰 등 접속 비밀은 Git 문서에 저장하지 않는다.

### CORE-REVIEW-01

**핵심 구현 점검·중대한 비효율 수정**

- 요청 배경: 전체 코드가 어떻게 구현됐는지 살피고 비효율을 최적화한다. 출시 전에는
  데이터 정합성·게임 진행·핵심 사용 흐름에 영향을 주는 범위를 우선한다.
- 다음 행동: 로그인, 그룹·방, 게임 시작·진행·종료, 재연결 흐름의 책임과 처리 경로를
  확인한다. 비용은 COST-01, 보안은 SECURITY-01에서 상세 결과를 관리한다.
- 완료 조건: 점검 범위와 근거를 남기고 출시를 막는 데이터 유실·진행 불가·중대한
  비효율을 수정·검증한다. 일반 구조 정리는 CODE-AUDIT-01과 CODE-OPTIMIZE-01로 연결한다.

### DOCS-CORE-01

**핵심 구조·개발·운영 문서 정비**

- 목적: 개발자와 에이전트가 현재 구현을 이해하고 안전하게 수정·검증할 수 있도록 한다.
- 다음 행동: 기존 아키텍처·개발·운영 문서와 코드·테스트의 누락·불일치를 확인한다.
- 완료 조건: 런타임 책임, 핵심 흐름, 권한·데이터·상태 전환의 경계, 검증·운영 경로를
  설명하고 실제 코드·테스트 링크와 확인 기준 커밋을 남긴다. 문서 목차와 AGENTS.md는
  같은 기준 문서로 안내한다. 일지 재분류만으로 이 구현 설명 작업을 완료하지 않는다.

### ROOM-CREATE-REQUEST-01

- **등록일·상태:** 2026-08-31 사용자 전달 사항. 미해결·수정 방향 검토 대기.
  기존 항목의 통과·차단 해제와 별도로 관리하며, 앞선 FULL PASS나 배포·실기기 결과로
  이 항목까지 해결됐다고 판단하지 않는다.
- **목적:** 방은 생성됐지만 앱이 응답을 받지 못해 재시도할 때, 요청 기록으로 중복 방
  생성을 막는다. 중복 방지 자체는 필요한 동작이다.
- **현재 문제:** 방과 요청 기록을 따로 삭제하므로 중간에 실패하면 요청 기록만 남을
  수 있다는 사용자 보고다.
- **누적 원인:** 방 없이 남은 요청 기록을 다시 찾아 정리하는 처리가 없다는 보고다.
- **검토할 점:** 방 생성·재시도 정책을 기준으로 별도 요청 기록을 유지하는 방식이
  꼭 필요한지 재검토한다. 유지한다면 부분 실패 뒤 정리·재처리 방안도 함께 검토한다.
  요청 기록 삭제나 대체 방식은 아직 결정하지 않았다.
- **확인 범위·다음 작업:** 이번에는 문서에만 기록했다. 코드 원인 확인, 운영 데이터의
  잔류·누적 규모 조회, 재현 테스트, 수정·배포는 수행하지 않았다. 사용자가 다음에
  전달할 추가 수정 사항과 함께 정리하고, 중복 방지 유지와 잔류 기록 처리의 검증
  조건을 정한다.

기존 `ROOM-CLEANUP-01`의 종료·유령 방 정리 문제와 구분한다. 해당 항목의 해결 기록과
통과 판정은 유지한다.

- 완료 조건: 중복 방 생성 방지와 잔류 기록 처리 방안을 확정하고 부분 실패·재시도·정리
  경로를 검증한다. 이전 ROOM-CLEANUP-01 통과를 이 문제의 해결 근거로 사용하지 않는다.

### RELEASE-EVIDENCE-01

**출시 증빙 보완 — 기존 문서의 미완료 확인 사항**

- 기존 Apple 로그인 성공은 팀원 전달 근거다. 정식 출시 기록에 확인자·기기·OS·빌드·
  날짜를 보완한다. 성공 판정을 취소하거나 새로운 실패로 바꾸는 작업이 아니다.
- 기존 세 시나리오의 통과 환경과 빌드는 [완료 기록](COMPLETED_TASKS.md)에 보존한다.
  미제공 정보는 추정하지 않고, 보고 환경 밖의 물리 태블릿·iOS·다른 게임까지 확대하지 않는다.
- 완료 조건: 확보한 증빙과 미확인 한계를 구분해 출시 기록에 연결한다. 추가 검증이
  필요하다면 대상·기기·빌드·시나리오를 정하고 별도 작업으로 관리한다.

### NET-RECOVERY-01 — 네트워크 복구 체감 지연

| 항목 | 값 |
| --- | --- |
| 상태 | 관찰 중 |
| 우선순위 | P2 |
| 출시 차단 | 아니오 |
| 담당 Issue | 착수 승인 시 생성 |

#### 현재 동작

- RTDB의 `.info/connected`가 복구되면 저장된 휴대폰 또는 controller 세션으로 같은 방의
  presence와 구독을 복원한다.
- 앱의 주요 복구 단계는 각각 8초 제한을 사용한다.
- 복구 중에는 안내 화면을 표시한다. 일시적인 문제라면 그대로 기다릴 수 있고, 기다릴
  수 없으면 `게임과 그룹 나가기`를 선택할 수 있다.
- 참가자 단절 판정은 별도 계약이다. 기존 10초 heartbeat와 `onDisconnect`를 유지하며,
  태블릿이 마지막 `lastSeen` 후 20초를 초과한 후보를 서버에 한 번 검증 요청한다.

이 항목은 **세션과 방 상태를 보존하며 복구에는 성공했지만 시간이 길게 느껴지는 경우**만
다룬다. 두 번째 단절 뒤 방·게임을 잃는 현상은 체감 개선이 아니라 출시 차단
`SESSION-RECONNECT-01`이다.

#### 지금 보류하는 이유

- 첫 단절은 30초 안에 앱 재시작 없이 같은 게임으로 복귀했다.
- 체감 시간에는 앱 코드뿐 아니라 OS 네트워크 전환과 Firebase SDK 재연결 시간이 포함된다.
- 상태를 보존한 단일 복구에서 출시를 막을 수준의 반복적인 지연 측정값은 아직 없다.
- 복구 안내와 명시적인 나가기 경로가 있어 앱이 무응답 상태로만 보이지는 않는다.

과거 반복 단절의 세션·방 유실에는 이 보류 근거를 적용하지 않았다. 수정 APK의
2026-08-31 라이어스포커 최종 테스트(Medium Tablet 에뮬레이터 + A32·A35)는 반복
단절을 포함해 통과했다. 순수한 체감 지연만 출시 후 관찰하며 상태 유실이 재발하면
다시 출시 차단 여부를 평가한다.

#### 우선순위를 올리는 조건

다음 중 하나가 확인되면 P1 또는 출시 차단 항목으로 재평가한다.

- 짧은 일시 단절 뒤에도 앱 재시작이 필요하다.
- SESSION-RECONNECT-01 수정 후에도 방, 게임 또는 남은 턴 상태가 유실된다.
- 일반적인 네트워크 전환에서 재연결이 반복적으로 30초 이상 걸린다.
- 같은 증상의 사용자 문의 또는 실제 세션 사례가 반복된다.
- Play Console, Crashlytics 또는 지원 기록에서 freeze·ANR·복구 실패가 확인된다.

30초와 반복 사례 기준은 최초 관찰 기준이며, 실제 배포 지표를 확보하면 조정한다.

#### 조사할 때 수집할 근거

- 단절 시작, `.info/connected` 복구, 세션 복원 완료 시각
- 휴대폰/태블릿 역할, OS, 네트워크 전환 종류
- 앱 재시작 필요 여부와 방·게임 상태 보존 여부
- 개인정보를 제외한 `[dev_error]`, `room_connection` 구조화 로그

production RTDB 관찰이 필요하면
[`Firebase MCP RTDB Read-only Pilot`](../operations/FIREBASE_MCP.md)의 사전 승인과
단일 경로 조회 절차를 따른다.

#### 완료 기준

- 짧은 단절 뒤 앱 재시작 없이 같은 방과 게임으로 자동 복귀한다.
- 게임 상태와 중단 시 보존한 남은 턴 시간이 유지된다.
- 측정한 복구 시간이 착수 시 합의한 목표 안에 들어온다.
- Android와 iOS 실제 기기에서 단절·복구 회귀 테스트를 완료한다.
- 관련 Flutter·Functions 자동 테스트와 Project CLI FULL validation이 통과한다.

### GAME-PAUSE-UX-01 — 단절 후 남은 시간 재개 안내

| 항목 | 값 |
| --- | --- |
| 상태 | 관찰 중 |
| 우선순위 | 출시 후 착수 시 결정 |
| 출시 차단 | 아니오 — 사용자가 해당 기능과 시나리오 전체를 통과로 명시 |
| 담당 Issue | 착수 승인 시 생성 |

#### 사용자 근거와 범위

2026-08-31 라이어스포커, `1.0.0-sessionfix.20260831+1` debug APK,
Medium Tablet 에뮬레이터 + Galaxy A32·A35에서 태블릿 중단 화면 뒤 30초를 기다려
네트워크를 복구했을 때 타이머가 6초 남아 있었다. 사용자는 서버가 멈춘 남은 시간부터
재개한 것으로 보이며 동작하고 반복 단절도 정상이라고 확인했다. 다만 사용자가 이
재개 방식을 납득할지에 대한 의견을 남겼다. 중단 직전 수치는 미제공이므로 정확히
몇 초가 보존·차감됐는지 추정하지 않는다. 기능 테스트 실패로 분류하지 않는다.

#### 착수 조건과 조사 계획

- 단절 감지 전 경과와 서버가 중단한 이후 보존 시간이 사용자에게 어떻게 보이는지 확인한다.
- 중단 화면의 남은 시간 표시와 복구 안내 문구 등 기존 타이머 계약 안의 개선을 먼저 검토한다.
- 비행기 모드 시작 시점으로 시간을 소급하거나 복구 시 시간을 추가·초기화하지 않는다.
  이러한 변경은 서버 판정·게임 공정성 계약에 영향을 주므로 별도 설계와 승인 대상이다.

#### 완료 기준

- 사용자가 멈춘 시점과 재개되는 남은 시간을 이해할 수 있는 안내를 실제 사용으로 확인한다.
- 기존 중첩 중단·반복 단절의 시간 보존 회귀 테스트를 유지한다.
- 별도 승인 없는 게임 시간 보정이나 상태 계약 변경이 없다.

### WINNER-CONNECTION-LAYER-01 — winner 아래 태블릿 연결 안내 겹침

| 항목 | 값 |
| --- | --- |
| 상태 | 관찰 중 |
| 우선순위 | 출시 후 착수 시 결정 |
| 출시 차단 | 아니오 — 사용자가 오류가 아닌 추후 개선으로 지정하고 통과 확정 |
| 담당 Issue | 착수 승인 시 생성 |

#### 사용자 근거와 범위

위와 같은 APK·게임·기기 조합에서 winner 표시 직후 태블릿 앱을 강제 종료하면,
winner 화면 아래에 사용자가 표현한 `태블릿 오류 화면`이 나타났다. 정확한 화면 문구,
해당 휴대폰과 route는 미제공이며 특정 widget의 문제라고 단정하지 않는다.
재시작 후 대기실 복귀·winner 닫힘·다음 게임 선택을 포함한 시나리오 3은 통과했다.
기존 검정 화면/복귀 실패인 FINISH-SYNC-01을 재개방하지 않는다.

#### 착수 조건과 조사 계획

- finished/winner 표시 중 controller 연결 안내가 뒤에 함께 나타나는 순서를 재현한다.
- 종료 결과 화면과 재연결 안내의 표시 우선순위를 조사하고 불필요한 중복 안내를 줄인다.
- 게임 진행 중 필요한 네트워크 안내, 그룹 나가기, 태블릿 복원·대기실 복귀를 보존한다.

#### 완료 기준

- winner와 controller 연결 안내가 혼란스럽게 겹치지 않는다.
- 태블릿 강제 종료·재시작 뒤 winner 닫힘과 전체 휴대폰 복귀 회귀가 없다.
- 관련 widget 테스트와 같은 시나리오의 기기 확인을 통과한다.

#### 사용자 근거와 범위

사용자는 이번 A32·A35 단절 테스트 이전 UT에서 실제 Galaxy S20+ 화면이 깨지지
않았음을 확인했다. 기존 깨짐은 저시력 사용자를 위한 기기의 글씨/화면 확대 설정
때문이었다는 설명이다. 기기 자체의 고정 해상도 문제로 단정하지 않는다. 당시 앱 빌드,
OS, 글꼴 크기·화면 확대 단계는 미제공이므로 원인 설명은 사용자 보고로 보존하고
구현 전 설정별 재현으로 확인한다.

현재 홈 제목의 줄바꿈 수정·일반 크기 테스트가 확대 설정 전체를 보장하지는 않는다.
사용자가 선택한 큰 글씨를 일괄 축소·차단하는 처리를 완료 기준으로 삼지 않는다.
이 항목은 단절·타이머·종료 실패와 분리하며 출시 차단 문제를 보류하는 근거가 아니다.

#### 착수 조건과 조사 계획

- 출시 차단 수정 이후 해당 빌드와 기기 설정값을 기록하고 확대 설정에서 재현한다.
- 글씨 크기와 화면 확대를 각각 바꾸고 함께 최대 단계로 설정한 경우도 확인한다.
- S20+와 A32·A35에서 홈의 `보유 중인 게임` 제목·설명부터 확인하고, 버튼·폼·확인창·
  게임/그룹 나가기 등 주요 조작의 잘림과 접근 가능 범위를 조사한다.
- 줄바꿈, 유연한 높이, 스크롤 등 기존 레이아웃 내 보완안을 우선 검토한다.
- 확대 설정 때문에 주요 조작이 불가능하다는 추가 근거가 나오면 우선순위와 출시 차단
  여부를 사용자와 재평가한다.

#### 완료 기준

- 기록한 기본·확대 설정 조합에서 overflow, 글자 잘림, 겹침이 없다.
- 큰 글씨에서도 내용과 핵심 버튼에 접근할 수 있고 시스템 확대 설정이 유지된다.
- 논리 화면 폭과 text scaling 조합의 관련 위젯 테스트 및 실제 기기 확인을 통과한다.
- 기기·OS·앱 빌드·글씨/화면 확대 단계와 결과를 남긴다. 이전 UT 결과로 새 빌드의
  검증을 대체하지 않는다.

## 출시 판정 기준

다음 조건을 모두 만족해야 이 문서의 출시 차단을 해제한다.

1. 신규 미해결 항목을 포함한 모든 차단 항목에 필요한 코드 수정과 관련 회귀 테스트가
   완료된다.
2. 관련 Flutter 분석·테스트와 Functions build·테스트가 통과한다.
3. Project CLI targeted suite와 `validate --full`이 통과한다.
4. 필요한 Functions만 승인된 절차로 배포하고 배포 후 동작을 확인한다.
5. 수정 완료 뒤 작성한 최종 실제 기기 체크리스트가 통과한다.
6. 실행 명령, exit code, 배포 함수, 실기기와 production 관찰 근거를 출시 기록에 남긴다.

위 기준은 기존 구현 변경의 출시 판정 조건을 보존한 것이다. 이 문서의 권장·출시 후
작업을 자동으로 출시 차단으로 올리거나 과거 통과 범위를 확대하지 않는다.
