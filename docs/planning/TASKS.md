# 작업 목록

현재 해야 할 일과 진행 상태의 단일 원본이다. 출시 시점은 문서 경계가 아니라 항목의
분류로 관리한다. 완료 결과는 [완료 문서](COMPLETED_TASKS.md), 과정은
[월별 기록](logs/), 현재 구현은 [아키텍처](../engineering/ARCHITECTURE.md)와
관련 기술 문서에서 확인한다.

## 관리 방법

- 작업 ID는 문서 이동·월 변경 후에도 유지한다. 상태는 `조사 전`, `요구사항 확인`,
  `관찰 중`, `진행 중`, `검증 대기`, `보류`로 구분하고, 보류에는 이유를 적는다.
- 사용자 보고, 코드·측정으로 확인한 사실, 원인 가설과 제안을 구분한다. 2026-08-31 신규
  항목의 등록일은 해당 날짜이며 이후 항목은 각 등록일을 적는다. 목록에 있다는 사실은
  조사·구현·승인 완료를 뜻하지 않는다.
- 필수 항목만 출시 차단으로 관리한다. 권장·출시 후 항목을 필수로 바꿀 때는 근거와
  결정을 기록한다. 비용·보안·핵심 구조 점검은 범위를 먼저 명시하고 무제한 최적화를
  완료 조건으로 삼지 않는다.
- 각 항목에 목적·현상, 완료 조건, 다음 행동, 관련 기록을 유지한다. 상세 진행은
  Issue/PR을 사용할 수 있지만 장기 결정과 완료 조건은 이 문서에 남긴다. 기존 출시 후
  관찰 항목은 착수 승인 시 Issue를 만들고 연결하는 절차를 유지한다.
- 완료 조건과 필요한 검증을 충족하면 상세 항목과 목록 행을 완료 문서로 옮긴다.
  완료일·변경 내용·검증 근거·한계를 남기고 들어오는 링크도 갱신한다. 일부만 완료하면
  남은 범위를 여기 유지한다. 취소는 완료와 구분해 이유를 기록한다.
- 기록은 `logs/YYYY-MM.md`에 태스크별로 모으고 각 태스크 안에서는 날짜순으로 쓴다.
  파일 상단에는 날짜별 링크 목차만 둔다. 여러 달의 기록 링크는 해당 작업/완료 항목에
  모은다. 공통 검증은 한 번 기록하고 관련 ID들에서 연결한다.
- 일지에는 의미 있는 조사·수정·실패·판단·검증만 남긴다. 검증은 명령, status, exit code,
  확인 범위와 필요 시 기기·빌드를 적고 credential·token·불필요한 사용자 데이터는 넣지 않는다.
- 현재 구현 설명을 일지로 대체하지 않는다. 구조·동작을 바꾸면 기존 기술 문서도
  갱신한다. 승인·검증은 [Engineering Contract](../engineering/ENGINEERING_CONTRACT.md)와
  [Project CLI](../engineering/PROJECT_CLI.md)를 따른다. 기록된 과거 승인을 새 작업에 재사용하지 않는다.

#### 분배 중 복원 판정과 로컬 세션 삭제

[복원 판정](../../lib/platform/home/room/services/room_common.dart)은 진행 중 게임에서

#### 다중 참가자 단절과 시간 보존

[중단 상태 처리](../../functions/src/game-interruption/state.ts)의 `beginGameInterruption`은
이미 다른 참가자의 중단이 있으면 추가 단절을 등록하지 않는다. A 단절 → B 단절 →
A 복귀 순서에서 A의 중단을 취소할 때 B의 단절 상태 전체를 다시 검사하지 않는다.
controller pause가 남아 있지 않다면 deadline을 복원할 수 있다.

이 코드는 `ea27b79` 이후 변경되지 않았다. 8월에 검증한 단일 참가자 반복 단절 및
참가자+controller 중첩 중단과, 여러 참가자 동시 단절은 서로 다른 경우다.
기존 시간 보존 통과를 취소하기보다 추가 실패 조건을 따로 관리해야 한다.

- 앞선 분석의 서버 메모리 실행에서는 A 단절 → B 단절 → A 복귀 때 B가 끊긴 채
  턴이 재개되는 조건을 재현했다. 운영 서버·실기기 재현과 구분한다.

#### 연결 복구·구독 재개·실제 준비 완료

`RoomProvider._performConnectionRecovery`는 controller/player presence를 복구하고
heartbeat를 시작하면 반환한다. 공개·개인 스냅샷이 같은 판·라운드의 최신 데이터인지,
권한 오류로 끝난 구독이 다시 열렸는지를 기다리는 계약은 없다.

[AppNetworkGuard](../../packages/game_kit/lib/core/network/app_network_guard.dart)는
`onRetry`가 정상 반환하면 입력 보호를 해제한다.
[GameSessionController](../../packages/game_kit/lib/game_flow/game_session_controller.dart)는
구독을 최초 `startSession`에서 열지만 오류로 끝난 구독을 다시 여는 경로가 없다.
연결 표시 정상화 뒤에도 화면이 굳거나 오래된 손패로 입력할 위험을 조사해야 한다.
일반적인 RTDB 자동 재연결과 취소된 구독 재생성은 구분한다.

#### 태블릿 최초 오프라인 복구

[TabletHome](../../lib/platform/home/tablet/screens/tablet_home.dart)은 `initState`에서
`restoreControllerRoom`을 한 번 호출한다. 실패하면 provider의 roomCode가 없는 상태로
남는다. lifecycle 복귀는 `resumeControllerPresence`만 호출하고, 이는 roomCode가 없으면
반환한다. 휴대폰 홈과 달리 최초 복구 실패 뒤 연결 true 이벤트로 저장 방 복구를 다시
시작하는 경로가 없다. 앱을 다시 열어야 복구가 재시도되는지 실기기 확인이 필요하다.

#### 일반 참가자의 그룹 대기실 게임 목록 — 회귀 근거

8월에는 클라이언트가 그룹 UID들의 `users/{uid}.ownedGames`를 읽어 합쳤다.
9월 1일 `b2bba19`에서 Firestore 사용자 문서를 본인만 읽도록 제한하면서 조회를
`fetchRealtimeRoomGroupEntitlements` callable로 옮겼다.

현재 호출 경로는 다음과 같다.

1. [RoomProvider](../../lib/platform/home/room/providers/room_provider.dart)의
   `listenRoom`이 태블릿·휴대폰 모두 `_refreshGroupGames`를 호출한다.
2. [GameService](../../lib/platform/home/gamelist/service/game_list_service.dart)의
   `fetchGroupGames`가 같은 callable을 인자 없이 호출한다.
3. [서버 함수](../../functions/src/room/realtime-room-lifecycle.ts)는 요청 UID를
   controller UID로 간주하고 `controllerRooms/{요청 UID}`를 조회한다.
4. 일반 참가자에게 이 매핑이 없으면 `failed-precondition`으로 실패한다. 다른 방의
   controller 매핑이 있으면 현재 참가한 방 대신 그 방을 기준으로 조회할 가능성도 있다.
5. 클라이언트는 목록을 비우고 failure 상태를 표시한다. 실패 후 UID 캐시를 지우므로
   다음 players 이벤트에서 같은 실패를 반복할 수 있다. heartbeat에 따른 반복 호출도 점검 대상이다.

태블릿과 같은 UID를 쓰면 controller 매핑 조건을 통과할 수 있어 사용자 보고와 맞는다.
같은 계정 로그인을 해결책으로 강제할 문제는 아니다. 일반 참가자의 해당 방 멤버십을
서버에서 확인하고 최소한의 게임 ID만 돌려주는 조회 계약을 보완할 필요가 있다.

단, 휴대폰 **홈**의 개인 목록은 `fetchGames`로 본인 소유·무료 게임만 조회한다.
태블릿 소유 게임이 다른 계정의 개인 홈 목록에 없는 것과, 같은 그룹 대기실의 목록 조회
실패는 구분해야 한다. 이번 원인 확인은 후자에 해당한다.

### NET-RECOVERY-01 — 네트워크 복구 체감 지연

| 항목 | 값 |
| --- | --- |
| 상태 | 관찰 중 |
| 우선순위 | P2 |
| 출시 차단 | 아니오 |
| 담당 Issue | 착수 승인 시 생성 |

#### 현재 동작

- RTDB의 `.info/connected`가 복구되면 저장된 휴대폰 또는 controller 세션으로 같은 방의
  presence와 구독을 복원한다.
- 앱의 주요 복구 단계는 각각 8초 제한을 사용한다.
- 복구 중에는 안내 화면을 표시한다. 일시적인 문제라면 그대로 기다릴 수 있고, 기다릴
  수 없으면 `게임과 그룹 나가기`를 선택할 수 있다.
- 참가자 단절 판정은 별도 계약이다. 기존 10초 heartbeat와 `onDisconnect`를 유지하며,
  태블릿이 마지막 `lastSeen` 후 20초를 초과한 후보를 서버에 한 번 검증 요청한다.

이 항목은 **세션과 방 상태를 보존하며 복구에는 성공했지만 시간이 길게 느껴지는 경우**만
다룬다. 두 번째 단절 뒤 방·게임을 잃는 현상은 체감 개선이 아니라 출시 차단
`SESSION-RECONNECT-01`이다.

#### 지금 보류하는 이유

- 첫 단절은 30초 안에 앱 재시작 없이 같은 게임으로 복귀했다.
- 체감 시간에는 앱 코드뿐 아니라 OS 네트워크 전환과 Firebase SDK 재연결 시간이 포함된다.
- 상태를 보존한 단일 복구에서 출시를 막을 수준의 반복적인 지연 측정값은 아직 없다.
- 복구 안내와 명시적인 나가기 경로가 있어 앱이 무응답 상태로만 보이지는 않는다.

과거 반복 단절의 세션·방 유실에는 이 보류 근거를 적용하지 않았다. 수정 APK의
2026-08-31 라이어스포커 최종 테스트(Medium Tablet 에뮬레이터 + A32·A35)는 반복
단절을 포함해 통과했다. 순수한 체감 지연만 출시 후 관찰하며 상태 유실이 재발하면
다시 출시 차단 여부를 평가한다.

#### 우선순위를 올리는 조건

다음 중 하나가 확인되면 P1 또는 출시 차단 항목으로 재평가한다.

- 짧은 일시 단절 뒤에도 앱 재시작이 필요하다.
- SESSION-RECONNECT-01 수정 후에도 방, 게임 또는 남은 턴 상태가 유실된다.
- 일반적인 네트워크 전환에서 재연결이 반복적으로 30초 이상 걸린다.
- 같은 증상의 사용자 문의 또는 실제 세션 사례가 반복된다.
- Play Console, Crashlytics 또는 지원 기록에서 freeze·ANR·복구 실패가 확인된다.

30초와 반복 사례 기준은 최초 관찰 기준이며, 실제 배포 지표를 확보하면 조정한다.

#### 조사할 때 수집할 근거

- 단절 시작, `.info/connected` 복구, 세션 복원 완료 시각
- 휴대폰/태블릿 역할, OS, 네트워크 전환 종류
- 앱 재시작 필요 여부와 방·게임 상태 보존 여부
- 개인정보를 제외한 `[dev_error]`, `[game_comm]`, `room_connection` 구조화 로그

production RTDB 관찰이 필요하면
[`Firebase MCP RTDB Read-only Pilot`](../operations/FIREBASE_MCP.md)의 사전 승인과
단일 경로 조회 절차를 따른다.

#### 완료 기준

- 짧은 단절 뒤 앱 재시작 없이 같은 방과 게임으로 자동 복귀한다.
- 게임 상태와 중단 시 보존한 남은 턴 시간이 유지된다.
- 측정한 복구 시간이 착수 시 합의한 목표 안에 들어온다.
- Android와 iOS 실제 기기에서 단절·복구 회귀 테스트를 완료한다.
- 관련 Flutter·Functions 자동 테스트와 Project CLI FULL validation이 통과한다.

### GAME-PAUSE-UX-01 — 단절 후 남은 시간 재개 안내

| 담당 Issue | 착수 승인 시 생성 |

#### 사용자 근거와 범위

2026-08-31 라이어스포커, `1.0.0-sessionfix.20260831+1` debug APK,
Medium Tablet 에뮬레이터 + Galaxy A32·A35에서 태블릿 중단 화면 뒤 30초를 기다려
네트워크를 복구했을 때 타이머가 6초 남아 있었다. 사용자는 서버가 멈춘 남은 시간부터
재개한 것으로 보이며 동작하고 반복 단절도 정상이라고 확인했다. 다만 사용자가 이

몇 초가 보존·차감됐는지 추정하지 않는다. 기능 테스트 실패로 분류하지 않는다.

#### 착수 조건과 조사 계획

- 단절 감지 전 경과와 서버가 중단한 이후 보존 시간이 사용자에게 어떻게 보이는지 확인한다.
- 중단 화면의 남은 시간 표시와 복구 안내 문구 등 기존 타이머 계약 안의 개선을 먼저 검토한다.
- 비행기 모드 시작 시점으로 시간을 소급하거나 복구 시 시간을 추가·초기화하지 않는다.
  이러한 변경은 서버 판정·게임 공정성 계약에 영향을 주므로 별도 설계와 승인 대상이다.

#### 완료 기준

- 사용자가 멈춘 시점과 재개되는 남은 시간을 이해할 수 있는 안내를 실제 사용으로 확인한다.
- 기존 중첩 중단·반복 단절의 시간 보존 회귀 테스트를 유지한다.
- 별도 승인 없는 게임 시간 보정이나 상태 계약 변경이 없다.

기존 검정 화면/복귀 실패인 FINISH-SYNC-01을 재개방하지 않는다.

#### 착수 조건과 조사 계획

- finished/winner 표시 중 controller 연결 안내가 뒤에 함께 나타나는 순서를 재현한다.
- 종료 결과 화면과 재연결 안내의 표시 우선순위를 조사하고 불필요한 중복 안내를 줄인다.
- 게임 진행 중 필요한 네트워크 안내, 그룹 나가기, 태블릿 복원·대기실 복귀를 보존한다.

#### 완료 기준

- winner와 controller 연결 안내가 혼란스럽게 겹치지 않는다.
- 태블릿 강제 종료·재시작 뒤 winner 닫힘과 전체 휴대폰 복귀 회귀가 없다.
- 관련 widget 테스트와 같은 시나리오의 기기 확인을 통과한다.

#### 착수 조건과 조사 계획

- 출시 차단 수정 이후 해당 빌드와 기기 설정값을 기록하고 확대 설정에서 재현한다.

  여부를 사용자와 재평가한다.

#### 완료 기준

- 기록한 기본·확대 설정 조합에서 overflow, 글자 잘림, 겹침이 없다.

### 원 검토에서 확인한 보호 장치

다음은 코드 존재·변경 이력 확인이며 최신 실기기 PASS 판정은 아니다.

- RoomProvider의 연결/세션 세대 검사, 퇴장 중 복구 무효화, 오프라인 heartbeat 건너뛰기는
  남아 있다. 반복 재접속 방어 전체가 삭제됐다고 판단할 근거는 없다.
- [RTDB rules](../../database.rules.json)의 presence 쓰기는 기존 active 참가자 노드를
  요구한다. 서버 `preserveProfile: true` 재접속도 기존 참가자 자격을 확인한다.
- 참가자 중단과 controller pause의 남은 시간 인계 로직은 남아 있다.
- [exitGameRoute](../../packages/game_kit/lib/widgets/game_route_exit.dart)의 inactive route
  재종료 방어와 태블릿 finished 방의 waiting 정리는 남아 있다.
- 10월 2일 `93892c0`은 공개 상태 구독의 권한 오류만으로 게임을 종료하던 경로를 완화하고,
  오래된 공개 revision·삭제 확인 응답을 무시하며 다시하기의 startedAt 변경을 반영했다.
  해당 보완을 현재 미수정 결함으로 다시 등록하지 않는다.
- 같은 commandId로 재전송하는 게임 행동의 기존 멱등 계약은 유지된다. 서버 응답 유실 후
  중복 행동·새 판에 늦게 도착한 요청은 구별해서 검증해야 한다.

### 권장 작업 순서와 확인 시나리오

1. 삭제된 핵심 회귀 테스트의 복원·이동 대응과 session/auth/FULL/CI 경로 정합성 복구.
2. 일반 참가자의 그룹 게임 목록 조회 권한 보완 및 역할별 통합 검증.
3. SESSION-RECONNECT-02의 플랫폼·서버·패키지 담당 범위와 복구 준비 완료 계약 합의.
4. 분배 중 재실행, 다중 단절, 취소된 구독 재개, 최초 오프라인 태블릿 복구 검증.
5. 옛 진행 요청의 새 판 도착, 재진입 연출, 퇴장·종료 화면 경합 검증.
6. 현재 후보 FULL과 Android/iOS 휴대폰·물리 태블릿 검증 근거를 출시 기록에 반영.

최소 재현 조합은 태블릿 T와 서로 다른 계정 휴대폰 A/B, T만 소유한 유료 게임,
A만 소유한 유료 게임, 무료 게임이다. 그룹 목록 동일성·참가/퇴장 시 갱신·권한 없는
외부 계정 차단을 확인한다. 세션 시나리오는 분배 중 강제 종료, A→B 동시 단절→A 복귀,
controller 단절 중첩, 권한 오류 후 복구, 오프라인 최초 실행, 완료 응답 유실 직후 다시하기다.

문서상 NET-RECOVERY-01의 단순 체감 지연은 세션 유실·복구 실패와 별개로 유지한다.
winner 안내 겹침·남은 시간 안내·확대 레이아웃도 기존 출시 후 분류를 유지한다.

원 검토의 코드 근거와 이미 보완된 보호 장치는 `fa4ad54` 시점의 조사 결과다.
이후 구현·운영 배포 여부를 재확인하며, [패키지 안정성 TODO](../../packages/GAME_STABILITY_TODO.md)의
10월 2일 보완을 미수정 결함으로 중복 등록하지 않는다. 서버/플랫폼의 외부 후속 범위는
SESSION-RECONNECT-02, 검증 배선은 TEST-REGRESSION-01에서 관리한다.
