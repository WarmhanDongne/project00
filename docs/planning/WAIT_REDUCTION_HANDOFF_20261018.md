## 1. 목표·범위·최신 결정

목표는 사용자가 느끼는 불필요한 대기를 줄이되 서버 승인·게임 규칙·복구 안전성을 보존하는 것이다. 이번 작업은 문서 인수인계 → 자료만으로 구현 가능한지 점검 → 새 브랜치에 문서만 반영한 중간점 → 항목별 구현 순서다. 아래 번호는 효과 예상치 순위가 아니다.

| 순서 | 항목 | 이번 인수인계의 실행 경계 |
| --- | --- | --- |
| 1 | 최초 자리 배치에서 DB 조회와 연출 병행 | 기존 합의 방향. 시작 성공 후 정리 대상 조회를 남은 착석/줌과 겹치는 앱 변경부터 구현한다. |
| 2 | 초기화 전 보조 취소 대기 분리 | 기존 합의 방향. 종료 의도 보존·옛 접속 수명 보호·실패 회귀가 성립할 때만 분리한다. |
| 3 | logger import 범위 축소 | 추가 후보. 현재 두 항목에 자동 편입하지 않는다. 별도 채택·실제 의존성 환경 대조 필요. |
| 4 | 게임 시작 중복 읽기 재사용 | 추가 후보. 서버 내부 helper 설계 가능. 별도 채택·회귀·배포 승인 필요. |
| 5 | 방 생성 독립 읽기 병행 | 추가 후보. 가입 확인과 매핑 읽기만 후보. 쓰기·오류 순서 보존 설계 후 별도 채택. |

사용자 예시의 ‘세 개선 후보’를 과거 폰 UI·준비 인스턴스·보조 취소 세 안으로 되돌리지 않는다. 최신 구분은 **기존 합의 2개 + 추가 후보 3개**다.

- **의도 확정:** 기준 카드 안내→카드팩, 착석·줌·배분·공개 연출은 유지한다. UI 방향은 미결정이 아니다.
- **보류 확정:** 준비 인스턴스 유지·주기적 예열은 비용 문제로 보류했다. 비용 비교를 새 구현의 선행 작업으로 요구하지 않는다.
- **제외:** 새 운영/RTDB 조회, 로그인·인증 접근, 배포·migration, 새 dependency 추가, 게임 규칙/공개·개인 데이터 이동 변경, 광범위 모듈 구조 개편.
- 제품 구현의 FULL 생략 승인은 없다. 과거 ‘FULL 생략’은 임시 계측 코드에 대한 결정이었다. 관련 체크 후 최종 후보의 FULL은 skill 절차에 따라 별도 승인받는다.

3. 함수명·호출자·상태 전이·기존 테스트로 현재 동작을 확인한다. 과거 줄 번호만 따라 편집하지 않는다. 변경이 있으면 의미 차이·안전 조건·측정 경계의 재검토 결과를 기록한 뒤 진행한다.

## 4. 항목 1 — 시작 성공 후 정리 대상 선조회

### 변경 지점과 현재 순서

- `lib/platform/home/tablet/tablet_game_start.dart`: 미확정 시작 확인 → 필요한 자리 저장 → 같은 시작 요청 확인/실행. 자리 저장과 시작의 의존성을 유지한다.
- `packages/game_kit/lib/player_layouts/widgets/player_layout_editor.dart`: [서버 준비 ∥ 착석 1.6초+0.25초 ∥ 배경 준비] → 줌 1초 → onComplete. 배경은 이미 병행이며 이를 새 개선으로 세지 않는다.
- `lib/platform/home/tablet/tablet_game_launcher.dart`의 `_buildStartSetup`/`prepare`/`complete`: 현재 complete에서 captureGameTarget을 await한 뒤 화면을 교체한다.
- `RoomProvider.captureGameTarget` → `RoomService.gameTarget`: controller identity 확인 → game/public.get → 방/접속/게임 문맥을 가진 정리 대상 반환.
- 게임 route 완료 → `room_restore_to_waiting.dart` → `clearCapturedGame` → 서버 `selectRealtimeRoomGame`의 방/게임 세대·finished 검증.

### 최소 설계

시작이 성공하고 같은 시도가 유효한 뒤 조회 Future를 시작한다. prepare의 성공 반환은 그 조회를 기다리지 않아 남은 연출과 겹치게 한다. complete는 해당 Future만 기다린 뒤 기존 방식으로 화면을 교체한다.

Future는 **시작 화면/route 수명에 귀속**해야 한다. `_buildStartSetup`의 매 build에서 초기화되는 지역 변수만으로 소유하지 않는다. rebuild·theme/provider 갱신으로 조회가 유실되거나 다른 시도로 넘어가지 않는 소유자를 두고 검증한다. 공용 TemplateGame의 반환형·서버 응답·공개 API를 넓히지 않는다.

- UID·roomInstanceId·controller/connection 신원·로컬 시도 토큰을 확인한다. 방 코드만 같다고 재사용하지 않는다.
- 성공 전 조회·미확정 요청의 새 ID 재발급·자리 저장 재전송을 하지 않는다.
- 늦은 완료/다른 방/계정/접속/새 시도는 폐기한다. 전환 자체가 낡으면 최신 게임을 대신 캡처하지 않고 옛 전환을 취소한다.
- 유효 시도에서 선조회가 실패하면 기존 전환 직전 확인으로 한 번 복귀한다. 그것도 실패하면 기존 nullable target 처리와 정리 생략 의미를 보존한다. 무한 재조회 금지.
- RoomProvider에 완전한 게임 세대 미러가 있다고 가정하지 않는다. 안전한 귀속 근거가 부족하면 원 경로를 유지한다.
- 조회 대상은 나중의 퇴장 정리용이다. 실제 게임 승인·손패 전달을 앞당기거나 게임을 미리 정리하지 않는다.
- 종료 시 기존 target의 게임 세대 검증과 퇴장 연출 후 정리 시점을 유지한다.

### 검증/채택

제어 가능한 Future로 ‘성공 후 조회 시작·조회보다 연출이 늦음·연출보다 조회가 늦음·실패 fallback’을 검증한다. 같은 시도의 rebuild·dispose·중복 탭·계정/방/접속 교체·동일 코드 새 방·미확정 시작 재확인을 포함한다. 실제 launcher 경로에서 기능이 연결되는 회귀도 확인한다. helper만 단독 통과했다고 완료하지 않는다.

기존 `game_command_response_loss_test.dart`, `room_restore_to_waiting_test.dart`, `tablet_room_reset_test.dart`와 공용 준비 화면의 네 게임을 확인한다. 메뉴/결과 재시작·복구 진입은 최적화 제외 경로이며 동작 불변을 확인한다. 조회 시작/끝·연출 끝·화면 첫 프레임·양쪽 입력 준비를 구분해 같은 조건에서 비교한다. 절감량은 실측 전 미정이다.

## 5. 항목 2 — 옛 접속 예약 취소를 종료 응답에서 분리

현재 `RoomService.closeControllerRoom`은 identity → cancel await → leaving/invalidate → durable close 저장/상태 확인 → closeRoom → confirmed → 같은 신원 정리 순서다. cancel 실패는 이미 무시하고 close를 수행한다. 서버 close는 자체 검증으로 권위를 가진다.

제안 순서는 **원 신원·정확한 접속 참조 고정 → 기존 종료 작업 재사용/안정적 intent 저장 → 같은 세션의 leaving/invalidate → [옛 cancel ∥ close/status] → 서버 확인 → 같은 신원만 정리**다. 이미 confirmed인 작업의 재생도 필요한 옛 예약 취소 의미를 유지한다.

### 보존 조건·위험

- `rooms/code/connections/uid/connectionId` 경로 자체에는 roomInstanceId가 없다. 정확한 참조 캡처만으로 새 접속 보호를 입증했다고 하지 않는다.
- 새 접속이 별도 ID를 쓰는지, 미완료된 옛 예약 등록이 나중에 같은 경로에 도착하는지 확인한다. 같은 경로의 등록/취소 수명 순서와 늦은 완료를 검증한다.
- 비동기 취소의 오류 처리기는 즉시 연결한다. 새 close 재시도와 다른 방 동작을 미완료 보조 Future에 묶지 않는다.
- RoomRecoveryBatch와 RoomActionTiming이 끝난 뒤의 보조 완료가 성공 샘플을 추가하거나 새 신원/session을 변경하면 안 된다. 실제 로컬 타이밍은 이미 늦은 완료를 억제하므로 이 보호를 유지한다.
- 저장 실패 때 close를 보내지 않는다. 서버 미확정 결과는 같은 operation ID와 복구 신원을 유지한다. 서버 확인 전 성공/빈 로비 표시 금지.
- 로컬 수명 보호로 안전하지 않으면 직렬 처리를 유지한다. Rules·세대/권한 검증을 완화하거나 새 영속 상태/TTL을 임의로 추가하지 않는다. 필요하면 그 항목만 보류하고 별도 설계를 제시한다.

### 검증/채택

`room_action_fast_path_test.dart`의 취소 fake에 지연·실패·미완료·늦은 완료를 주입한다. 첫 close 1회·미확정 status applied/stale/notApplied·원 ID 재시도를 유지한다. 원 의도 저장 완료 전 전송 없음, 서버 실패/응답 유실 시 신원 보존, 새 방·접속·계정·옛 등록 경합을 검증한다. `tablet_room_reset_test.dart`의 성공 전 UI/중복 종료 보호도 확인한다.

cancel·close 시작/응답·태블릿/폰 완료를 따로 재서 기여를 확인한다. 기여가 작으면 성능 변경으로 채택하지 않는다. 게임 나가기/참가자 퇴장으로 범위를 확대하지 않는다.

## 6. 추가 후보 3개의 후속 설계 경계

- **중복 읽기:** `replayGameCommand`의 첫 snapshot과 저장 응답을 내부 helper로 함께 얻어 LP start에서 재사용하는 안. 기존 wrapper 소비자·동일 요청 재생·최종 transaction/fingerprint/첫 value priming 유지. 저장된 응답 재생의 검사 순서를 바꾸지 않는다. 서버 배포는 별도 승인.
- **생성 독립 읽기:** onboarding과 previous_mapping의 읽기만 병행. 기존 사용자 정보 보완 저장까지 성공하기 전 생성 쓰기 금지. 시작한 읽기는 실패 응답 전 settle, 오류 우선순위 유지. 예약/세대/CAS·후속 재검증을 제거하지 않는다.

추가 후보의 채택·실측 효과·DB/네트워크 변동의 분해는 미결정이다. UI 연출 보존과 준비 인스턴스 보류를 미결정으로 되돌리지 않는다.
