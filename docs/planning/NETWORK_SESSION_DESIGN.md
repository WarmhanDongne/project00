### 5.1 P1~P3 상세 동작 명세

사용자는 2026-10-08 권장안을 받아들이고 세 정책의 상세 명세를 요청했다.
다음은 합의한 상위 정책에서 도출한 동작 기준이다. 신규 준비 확인 메시지·저장 필드·반영 방식을 선택하거나 구현한 것은 아니다.

#### P1 — 중단 대상과 중단 시점

1. 적용 대상은 진행 중인 게임의 태블릿 controller와 서버가 생존 참가자로 판정한 사용자다.
   현재 턴 여부와 관계없이 포함한다. 탈락자·관전자는 전체 진행을 막는 준비 대상에서 제외하지만,
   본인 기기의 복구·권한 확인·입력 보호는 계속 필요하다. Holdem 올인 stack=0을 곧바로 탈락으로 해석하지 않는다.
   게임별 생존 판정과 최소 인원은 P9에서 별도로 확정한다.
2. 분배·행동·발표·결과 연출 등 진행 중인 판의 단계에도 같은 중단 원칙을 적용한다.
   이미 게임 전체가 최종 종료된 경우에는 턴을 복원하거나 게임을 재개하지 않는다.
   대기실·새 게임 시작 전 준비는 해당 흐름의 별도 설계 범위다.
3. 기기의 오프라인 감지는 본인 입력을 먼저 보호할 수 있지만, 전체 게임 중단의 권위 시점은
   서버가 현재 방·판·멤버십·최신 접속 상태를 확인하고 중단을 반영한 시점이다.
   참가자의 기존 onDisconnect·heartbeat stale 재검사와 태블릿 presence 감지를 사용하되,
   이 정책으로 감지 임계값을 새로 바꾸지 않는다. stale 20초는 참가자 후보 확인 기준이며
   모든 기기의 확정 단절 시간이거나 감지 지연의 최대 보장이 아니다. 감지 뒤 별도 유예는 추가하지 않는다.
4. 서버가 게임을 중단할 때 남은 시간을 저장하고 게임 진행을 함께 멈춘다.
   카드 행동·분배 완료·결과 완료·턴 만료 요청은 자동 요청을 포함해 처리하지 않는다.
   재접속·준비 확인·본인 퇴장·진행자의 제외/종료 요청은 권한과 현재 상태를 확인해 처리한다.
   중단 전에 이미 처리한 정상 행동은 되돌리지 않는다.
5. 중단 중 다른 대상 기기도 끊기면 해당 단절을 추가로 기록하고, 처음 저장한 남은 시간은 유지한다.
   남아 있는 중단 사유가 모두 해결되고, 태블릿과 생존 참가자의 연결·필수 준비가 확인돼야 게임을 재개한다.
   제외된 참가자는 준비 대상에서 빼고 남은 인원으로 진행 가능한지 확인한다.
   늦게 도착한 단절·복귀 알림은 현재 상태를 확인한 뒤 처리하고, 같은 단절 신고는 중복 기록하지 않는다.

#### P2 — 필수 준비와 재개 시점

재개는 아래 조건을 모두 충족했을 때 서버가 결정한다.

| 확인 대상 | 준비 완료의 의미 |
| --- | --- |
| 자격·연결 | 태블릿 controller 세션과 참가자의 현재 방·게임 자격이 유효하고 서버가 확인한 최신 접속 상태가 정상 |
| 데이터·구독 | 필요한 구독이 정상이고 해당 방·판·라운드/핸드·단계의 필요한 공개 데이터와 본인 개인 데이터가 일관되게 해석 가능. 서버 전용 정보는 클라이언트에 요구하거나 공개하지 않음 |
| 화면 | 현재 단계를 표시하고 재개 신호 뒤 해당 역할의 조작을 받을 수 있음. 폐기된 화면·이전 route·이전 복구 작업의 완료는 준비 근거가 아님 |
| 에셋 | 현재 단계를 이해하고 조작하는 데 필요한 파일이 사용 가능한 상태. 장식 효과·배경음·완료된 시작 연출 재생은 재개 대기 조건으로 만들지 않음. 필수 파일 목록과 다운로드 정책은 P8 및 게임별 상세 설계에서 확정 |
| 서버 재검사 | 모든 유효 중단 사유가 해소되고 남은 참가자가 게임 규칙상 진행 가능. 준비 통지는 현재 복구 회차·세션·판에 대한 것으로 확인 |

- 필요 데이터는 역할·단계별로 판단한다. 태블릿은 참가자의 private를 읽지 않는다.
  LP·FC 분배 중처럼 private가 아직 없어야 하는 단계에서 private 존재를 강제하지 않는다.
  반대로 손패가 필요한 행동 단계에서 누락을 정상 준비로 취급하지 않는다.
- 인터넷 연결·presence true·heartbeat 재개·에러 문구 삭제는 단독 준비 완료 근거가 아니다.
  준비를 마친 기기도 전체 게임 재개 결정 전에는 게임 행동을 적용하지 않는다.
- 준비 대상은 태블릿과 현재 생존 참가자 전원이다. 기존 온라인 기기도 현재 복구 회차의
  상태에 준비됐다는 유효한 근거가 필요하다. 이미 유효한 준비 근거를 계속 인정하는 방식과
  새 확인을 받는 방식은 상세 기술 설계에서 선택한다.
- 복구 중 재단절·UID/controller 세션 변경·방/판/필수 진행 상태 변경·화면 dispose가 발생하면
  영향을 받은 준비 근거를 무효화하고 다시 확인한다. 단순 ready 메타데이터 변화만으로
  준비 확인을 무한 반복하도록 만들지 않는다.
- 한 기기의 준비 실패·미확인은 중단 사유로 남는다. 단절자가 서버에서 정당하게 제외되면
  대상 집합을 갱신하고 남은 사유·진행 가능 인원을 다시 검사한다. 마지막 사유가 해소돼야 재개한다.
- 서버 재개 상태를 수신하고 현재 판·역할과 일치함을 확인한 기기부터 로컬 입력을 허용한다.
  준비 확인 전후에도 실제 통신 지연은 존재하므로 전 기기 신호 수신의 물리적 동시성까지 보장하는 정책은 아니다.
- 데이터 최신성·준비 확인을 증명하는 방법은 현 계약에 공백이 있으므로
  서버·플랫폼·패키지 소비자 영향 분석 뒤 정한다. 클라이언트의 준비 주장은 게임 상태를 변경할 권한이 아니다.

#### P3 — 시간 보존

- 최초 서버 중단 시각을 tPause, 당시 진행 중인 턴의 서버 마감을 deadline이라 하면
  유효한 타이머의 보존 시간은 `max(0, deadline - tPause)`다. 기기 시계로 계산·보정하지 않는다.
- 중단부터 데이터·화면·에셋 준비를 마칠 때까지 턴 시간은 차감하지 않는다.
  추가 단절·순서가 다른 복구·재시도·중복 이벤트는 이 보존값을 다시 계산하거나 덮어쓰지 않는다.
- 동일한 턴의 최종 서버 재개 시각이 tResume이면 새 마감은 `tResume + 보존 시간`이다.
  재개 이후 신호 전달 지연과 정상 플레이 시간은 다시 경과한다. 전송 성공 시점이나 안내 화면이 닫힌 시점으로
  마감을 기기마다 따로 만들지 않는다.
- 예: 기기 단절 당시 20초, 서버 중단까지 5초 경과 → 15초 보존.
  연결 복구와 필수 준비에 총 40초가 걸려도 재개 시 서버 기준 15초가 남는다.
  재개 후 4초 정상 진행하고 다시 중단하면 다음 보존값은 11초다.
- 서버 중단 전에 이미 시간이 만료됐다면 보존값은 0이다. 복구했다고 시간을 추가하지 않는다.
  해당 턴의 만료 처리는 중단 해소 후 게임 규칙대로 수행하며 경합은 서버 상태 전이로 직렬화한다.
- 원래 타이머가 없는 단계의 deadline 누락은 0초 만료와 다르다. 없는 타이머를 복구 시 새로 만들지 않는다.
- 기존 턴 유지: 남은 시간부터 재개
- 다른 참가자의 새 턴: 게임 기본 턴 시간 부여
- 게임 종료: 타이머 재개하지 않음
- 다른 중단 사유 존재: 타이머 정지 유지, 최종 재개 시점부터 차감
- 회귀 검증: 참가자 제외·중첩 중단·재단절 상황에서도 기존 동작 보장
- 여기서 보존하는 것은 게임 턴/진행 시간이다. 중단 투표·제외 대기시간, 방 보존·정리시간,
  네트워크 재시도 timeout까지 모두 정지시키는 정책은 아니다. 해당 시간은 후속 정책에서 각각 정한다.

#### 대표 상태 흐름

| 사건 | 전체 진행 | 시간·준비 처리 |
| --- | --- | --- |
| 서버가 A 단절을 확정 | 중단 | 최초 남은 시간 보존, A 복구 대기 |
| 서버가 B 또는 태블릿 추가 단절을 확정 | 중단 유지 | 사유 추가, 보존값 유지 |
| A 연결만 복구 | 중단 유지 | A 필수 준비 확인 진행 |
| A 준비 완료, B 또는 태블릿 미준비 | 중단 유지 | A 준비 근거 유지, 남은 사유 대기 |
| 마지막 대상 준비 완료 | 서버 재검사 후 재개 | 동일 턴 보존 시간으로 마감 복원 |
| 대상 제외·게임 종료 | 서버가 결과 판정 | 남은 대상 재검사 또는 종료. 종료된 게임은 재개하지 않음 |

#### 이 합의로 확정하지 않은 것

다중 단절의 만료 후 연장 상세,
퇴장 취소·재시도 상세, 에셋 다운로드 방식, API·저장 구조는 별도 설계한다.
미준비 상태를 영구 대기로 만들지 않도록 P5·P6·P8의 실패·종료 정책을 이어서 합의해야 한다.
상위 정책 합의만으로 SESSION-RECONNECT-02의 담당 범위 보류나 전체 완료 판정을 해제하지 않는다.

### 5.2 P5 — 참가자 대기와 만료 후 진행자 선택

#### 합의 및 사용자 지정

- 참가자의 기본 대기 마감은 서버 단절 확정부터 연결·필수 데이터·화면·에셋 준비까지 총 60초다.
  각 참가자에게 별도 마감을 두며, 다른 참가자의 단절이나 기존 복구의 재시도로 그 마감을 초기화하지 않는다.
- 사용자는 대기 만료 전 조기 제외를 허용하고 조기 제외 버튼은 태블릿에만 배치하도록 지정했다.
  진행자는 기본 60초 또는 선택한 추가 30초가 끝나기 전에도 해당 참가자의 제외를 요청할 수 있다.
  따라서 기본·추가 대기는 진행자의 조기 제외 선택으로 끝날 수 있으며 무조건 기다려야 하는 최소 보장 시간이 아니다.
  제외는 기존 서버 권한·현재 대상 상태·게임별 진행 가능 조건 검증을 따른다.
- 사용자는 휴대폰 참가자의 중단 제외 투표와 인원 부족 시 전체 게임 즉시 종료 권한을 없애기로 합의했다.
  휴대폰은 복구를 기다리거나 본인이 게임과 그룹을 나갈 수 있다. 다른 참가자의 제외와 전체 게임 수동 종료는
  유효한 태블릿 진행자가 결정한다. 본인 퇴장에 따른 기존 게임 규칙상의 종료는 별개로 유지한다.
  제거 대상은 게임 중단 해결을 위한 투표이며, 마피아 등 게임 규칙 자체의 투표는 해당하지 않는다.
- 마감까지 준비되지 않은 참가자를 자동 제외하거나 이 마감만으로 자동 게임 종료하지 않는다.
  태블릿에 해당 참가자를 표시하고 진행자가 단독으로 다음 행동을 선택한다.
  다른 참가자의 찬성 투표를 만료 후 결정의 필수 조건으로 요구하지 않는다.
- 선택지는 `더 기다리기`, `해당 참가자를 제외하고 계속하기`, `게임 종료`다.
  사용자는 더 기다리기 선택 시 30초 추가 대기를 제안한 뒤 한 번만 연장하도록 결정했다.
  해당 참가자의 같은 중단에 대한 연장 한도이며, 다른 참가자의 연장 기회를 소모하지 않는다.

#### 30초 연장 및 선택 처리 — 합의와 남은 상세

2026-10-09 서버가 더 기다리기를 수락한 순간부터 30초를 부여하는 기준과,
만료 후 선택 전 해당 참가자가 필수 준비를 완료하면 안내를 해소하고 전체 준비 시 자동 재개하는 기준을 합의했다.
인원 부족 버튼 조건도 후속 Q15에서 합의했다. 게임별 인원 기준·서버 요청 경합·중복 처리 등의 나머지 상세는 기술 설계에서 확인한다.

| 선택 | 권장 동작 |
| --- | --- |
| 더 기다리기 | 서버가 현재 controller 권한·판·중단 대상·마감 상태를 확인해 선택을 수락한 시각부터 해당 참가자의 대기를 30초 연장. 이미 지난 마감에 30초를 더하지 않는다. 다른 참가자의 마감과 보존 턴 시간은 바꾸지 않음 |
| 해당 참가자를 제외하고 계속하기 | 서버가 현재 참가·준비 상태와 제외 후 게임 규칙상 진행 가능 여부를 확인. 가능한 경우 제외하고 남은 중단 사유·필수 준비를 재검사. 다른 미준비 대상이 있으면 전체 진행은 계속 중단 |
| 게임 종료 | 서버가 유효한 controller의 종료 선택을 반영하고 모든 기기의 종료·복귀 흐름으로 연결 |

- 30초 연장은 한 번만 허용한다. 연장 시간도 만료되면 `더 기다리기`를 다시 제공하지 않고
  `해당 참가자를 제외하고 계속하기`와 `게임 종료`를 표시한다.
  제외 후 진행 인원이 부족하면 제외 후 계속을 비활성화하고 게임 종료만 제공하는 것으로 후속 합의했다.
  선택 전에 정상 준비되면 아래의 복구 처리 원칙을 따른다.
- 기본 60초와 추가 30초는 복구·준비를 기다리는 시간이다. 진행자가 선택하기까지 걸리는 시간은
  별도로 존재하므로 최초 단절부터 실제 제외/종료까지 항상 90초 이내라고 보장하지 않는다.
  대기 선택 상태에서도 보존된 턴 시간은 차감하지 않는다.
- 제외 후 게임 규칙상 진행 인원이 부족하다면 `제외하고 계속하기`는 비활성화하고 이유를 표시하는 것으로 합의했다.
  연장 1회가 남으면 더 기다리기·게임 종료, 연장을 소진했으면 게임 종료를 제공한다. 서버도 같은 조건을 검사한다.
- 선택 화면이 떠 있어도 복구·준비 확인은 계속한다. 선택 전에 해당 참가자가 정상 준비되면
  그 대상의 선택 요구를 해소하고 전체 재개 조건을 다시 검사한다. 모든 필수 기기가 준비됐으면
  서버가 자동 재개하고, 다른 중단 사유가 남으면 계속 중단하는 것으로 합의했다.
  정상 복구한 참가자를 늦은 요청으로 제외하지 않는 서버 경합 처리는 후속 기술 설계에서 정한다.
- 여러 참가자가 만료되면 대상별 상태·선택을 구분한다. 한 명의 연장이 다른 사람의 마감을 초기화하거나
  한 명의 제외가 전체 게임 즉시 재개를 뜻하지 않게 한다.
- 연장·제외·종료 요청 중 중복 클릭과 응답 유실은 서버의 동일 작업 확인으로 처리한다.
  이전 판·이전 마감에 대한 선택은 새 판·갱신된 대기에 적용하지 않는다.
- 진행자가 선택하지 않는 동안은 중단을 유지하는 방향이다. 태블릿 자체의 단절은 아래 합의대로 처리하며,
  기존 방 보존/cleanup을 이 참가자 정책만으로 무기한 해제하지 않는다.

#### 태블릿 자체 단절 — 합의

- 태블릿이 끊겨 진행자가 결정을 내릴 수 없으면 게임 진행·턴 타이머의 중단 상태를 유지한다.
  게임 상태와 보존 시간을 기존 서버의 방 보존 한도 안에서 유지하며,
  참가자의 60초·추가 30초 정책을 태블릿 자체의 자동 종료 제한시간으로 적용하지 않는다.
- 휴대폰에는 `복구 기다리기`와 `본인이 게임과 그룹 나가기`를 제공한다.
  본인 나가기는 해당 참가자의 퇴장 요청이며 다른 참가자의 제외나 전체 게임 종료 권한을 부여하는 것은 아니다.
  참가자 퇴장으로 발생하는 기존 최소 인원·게임 규칙상의 종료는 유지한다.
- 이 단절만을 이유로 별도의 짧은 제한시간 뒤 전체 게임을 자동 종료하는 정책은 추가하지 않는다.
  기존 서버의 방 보존·정리 규칙은 유지한다. 현재 checkout은 playing 방의 controller lastSeen으로부터
  15분이 지나면 정리 대상이 된다. 실제 정리는 스케줄과 최신 상태 재검사에 따르므로 정확히 15분에 삭제된다는 보장은 아니다.
- 태블릿이 복귀하면 유효 controller 세션·현재 판·필수 준비를 확인하고,
  남은 참가자 중단 사유와 전체 재개 조건을 다시 검사한다. 그 사이 참가자 마감이 지났다면
  복귀한 진행자가 최신 대상에 대해 합의한 선택을 수행한다. 이미 종료·정리된 방은 되살리지 않는다.
- 태블릿이 연결돼 heartbeat는 정상인데 필수 준비가 실패한 경우는 단절에 따른 방 정리와 같지 않다.
  준비 실패의 재시도·종료 안내는 P6·P8에서 추가 설계한다.

#### 기존 구현과의 차이 및 남은 범위

- 현재 expire-resolution.ts는 마감이 지나면 canContinue에 따라 자동 제외·계속 또는 인원 부족 종료를 처리한다.
  expire callable과 cleanupExpiredGameInterruptions 스케줄이 같은 함수를 사용한다.
  UI만 바꾸면 서버 자동 처리와 충돌하므로 서버·플랫폼·패키지를 함께 설계해야 한다.
- 조기 제외 허용과 태블릿에만 버튼 배치, 휴대폰의 중단 제외 투표·전체 게임 즉시 종료 권한 제거를 합의했다.
  버튼을 숨기는 것만으로 끝내지 않고 서버 권한도 새 정책과 맞도록 설계한다.
  진행자의 일반 게임 종료는 기존 태블릿 설정 메뉴에서 현재 게임을 수동 종료하는 기능이며,
  단절자를 제외하고 계속하기·본인 그룹 나가기·방 전체 닫기와 구분한다.
  사용자는 대기 만료를 기다리지 않고 정상 진행/중단 중에도 해당 종료 권한을 유지하는 권장안을 수락했다.
  유효한 controller 권한과 현재 판을 서버가 검증하며, 끊긴 태블릿의 요청 성공을 보장한다는 뜻은 아니다.
  이 정책의 참가자별 마감·연장·진행자 선택 상태 및 현재 요청·스케줄의 영향은 후속 기술 설계에서 확인한다.
- 정책 기록 단계다. 제품 코드·API·저장 데이터·배포를 변경하지 않았다.

### 5.3 P4 — 앱 재실행 후 복귀

- 2026-10-08 사용자는 휴대폰 재참여 확인·태블릿 자동 복구의 1번 권장안을 수락했다.
  앱을 종료하지 않은 순간 단절은 기존 화면에서 자동 복구하는 전제를 유지한다.
- 휴대폰은 이전 세션으로 복귀할지 확인하고, 수락 후 현재 참가 자격·판·필수 준비를 확인한다.
  태블릿은 별도 재참여 질문 없이 현재 controller 세션과 방 상태를 확인해 복구한다.
  복귀 선택이나 연결 회복만으로 전체 게임을 재개하지 않으며 P2의 준비 조건을 적용한다.
- 재실행이나 질문 응답 대기로 기존 참가자 중단 마감을 초기화하지 않는다.
  종료·정리된 방이나 제외된 참가자를 복귀 과정에서 되살리지 않는다.
- 휴대폰에서 `다시 참여하지 않기`는 본인 게임·그룹 퇴장을 요청하는 것으로 합의했다.
  서버가 실제 퇴장과 기존 게임 규칙의 다음 턴·인원 부족 종료를 처리한다.
  해당 참가자의 퇴장만으로 다른 중단 사유를 해제하거나 전체 재개를 확정하지 않는다.
- 현재 phone_home.dart와 RoomProvider.declineRestorableSession은 로컬 저장 세션만 지우며
  서버 퇴장을 요청하지 않는다. 합의한 거절 동작과의 차이이며 구현은 아직 변경하지 않았다.
  퇴장 요청 결과를 확인할 수 없는 경우는 아래 P7 합의를 적용한다.

### 5.4 P7 — 퇴장 결과 미확정

- 2026-10-08 사용자는 퇴장 의도를 유지하는 권장안을 수락했다.
  퇴장 요청의 응답이나 결과 조회가 실패해도 서버 미처리 또는 퇴장 완료로 단정하지 않는다.
- 게임 자동 복귀와 게임 입력을 막고 `퇴장 확인 중`을 표시한다.
  이 상태에서도 결과 확인·재시도에 필요한 연결과 조회는 가능해야 한다.
- 연결이 돌아오면 서버의 현재 결과를 확인한다. 퇴장이 완료됐으면 퇴장 완료 흐름으로 정리하고,
  미처리라면 재시도할 수 있게 한다. 확인 자체가 다시 실패하면 미확정 상태와 퇴장 의도를 유지한다.
- 본인 게임·그룹 나가기와 복귀 거절에 따른 동일 퇴장 요청에 적용한다.
  네트워크 오류만으로 퇴장 의도를 생성하지 않는다. 나가기를 선택하지 않은 사용자는
  연결 회복 후 P2의 필수 준비·전체 재개 조건에 따라 게임 복구를 계속한다.
  게임 참가 상태와 방 멤버십의 의미를 구분해 결과를 확인하며, 다른 참가자의 중단·게임 진행은
  서버의 기존 게임 규칙과 전체 재개 조건을 따른다.
- 현재 _hasLeftDespiteFailure는 조회 실패도 false로 반환한다. _runLeave는 이 경우
  RoomLeaveIntent.fail과 heartbeat 재시작을 수행하므로 합의한 미확정 정책과 차이가 있다.
  이 단계에서는 차이와 제품 목표만 기록하며 구현을 변경하지 않았다.
- 사용자는 이미 보낸 퇴장 요청의 결과 미확정 중 취소를 제공하지 않는 1번안을 수락했다.
  동시에 네트워크 회복 후 게임을 계속할 수 있는데 퇴장하는 상황의 의미를 질문했다.
  명시적 나가기 선택과 네트워크 오류 자체를 구분해 설명하고, 요청을 확실히 보내지 않은 상태까지
  취소 금지를 적용할지는 추가 결정한다. 오프라인 표시만으로 요청 미전송을 확정하지 않는다.
  후속 답변에서 사용자는 오류만 발생하면 복구·재개, 명시적 나가기 선택 시 연결 회복 후 퇴장 처리라는
  두 가지 적용 기준으로 진행하도록 지정했다. 확실한 미전송 상태의 취소 허용 제안은 수락하지 않았다.
- 재시도 횟수·간격·확인 시간 예산은 P6과 연결한다.
  2026-10-09 앱 재실행 후에도 퇴장 의도를 보존하고 결과 확인을 이어가며 게임 자동 복귀를 막는 것으로 합의했다.
  동일 계정·해당 세션의 미확정 퇴장에 적용하고 의도 보존 방식·저장 계약·요청 식별자는 후속 기술 설계에서 정한다.
- 2026-10-09 후속 R03에서 사용자는 대안을 선택했다. 확실한 미전송 상태에서도 나가기 선택을 유지하고
  취소를 제공하지 않는다. 연결 회복 후 필요한 결과 확인·퇴장 처리를 계속한다.

### 5.6 P8 — 복귀 확인 합의와 에셋 검토 결과

- 태블릿 상세·스토어 화면에서 기존 게임 복구가 가능해지면 사용자에게 복귀 여부를 묻고,

  복귀 필요 상태를 보존하고, 동의 시 현재 controller 세션·방·판·필수 준비를 다시 검사한다.
  2026-10-09 사용자는 거절을 현재 게임·방 나가기로 지정했다. 화면만 닫거나 복귀 안내만 숨기지 않는다.
  태블릿은 controller이므로 일반 참가자의 본인 퇴장과 구분한다. 현재 서버 closeRoom은 방을 closed로
  전환하고 controller 매핑을 해제하는 방 전체 종료 경로다. 게임·방 종료 요청의 정확한 배선은
  후속 기술 설계에서 정하며, 요청 결과 미확정 시 의도 유지·자동 복귀 차단의 P7 정책을 적용한다.

  인터넷 단절 자체가 저장 파일을 지우는 경로는 조사한 에셋·연결 복구 코드에 없으며,
  현재 prepareGame은 로컬 검증만 수행한다. 초기 진입뿐 아니라 앱 재실행 후에도
  저장한 매니페스트로 로컬 파일을 검증할 수 있다.
- 다만 현재 모든 게임의 모든 에셋 준비를 진입 전에 검증 완료한다고 단정할 수는 없다.

  일부 이미지·사운드 사전 로딩은 진입 후 비동기로 수행한다. P2의 실제 화면 준비 계약은 여전히 필요하다.
  기존 파일을 다시 읽거나 디코딩하는 작업은 재다운로드와 구분한다.
- newgui 후보의 helper도 로컬 검증 성공 시 곧바로 반환한다. 검증 실패 시에만 다운로드를 시도하며,
  cache.install은 유효한 파일을 다시 받지 않는다. helper 호출만으로 정상 복구의 재다운로드를 주장하지 않는다.

R11~R15 기술 계약·그룹 목록, R16~R18 담당/채팅 완료 단위/테스트 계획과 측정 후 성능 목표 수치는 추가 설계·합의 대상이다.
